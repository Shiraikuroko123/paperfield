# M4.7 专题：具身智能与 LLM Agent

> 锚点：SayCan（Google, 2022）；前置：M4.5 VLM 到 VLA 专题 Q1 的分层 vs 端到端之争，本课展开

## 一、问题：大脑很聪明，但它没有手感

LLM 知道"打扫厨房"该先收碗再擦台面——**任务级规划知识互联网上有**。但它不知道：眼前这台机器人够不够得着碗？夹爪现在拿着东西吗？这叫 **grounding 问题（接地问题）**：语言知识与物理现实脱节。LLM Agent（写代码、订机票）的工具是 API，调用必成功；机器人的"工具"是自己的身体，每个动作都可能失败——这是两种 Agent 的本质分界。

## 二、SayCan：接地问题的开山解法

思路优美，一行公式记住它：

**选技能 = argmax [ LLM 觉得该做(Say) × 价值函数觉得能做成(Can) ]**

- Say：LLM 给每个候选技能打分——"对完成'饮料洒了帮我处理'，'去拿海绵'有多有用？"
- Can：每个技能配一个价值函数（affordance），评估"当前状态下这个技能的成功概率"
- 两分数相乘选技能，执行后重新规划

例子：饮料洒了，LLM 可能说"拿吸尘器"（语言上合理），但 Can 函数知道附近没有吸尘器、海绵就在手边 → "拿海绵"胜出。**语言的合理性被物理的可行性修正**——这就是接地。

## 三、SayCan 之后的演化树

- **Inner Monologue**：把执行结果（成功/失败/看到什么）用语言喂回 LLM → 闭环重规划（SayCan 是开环的）
- **Code as Policies**：LLM 直接写策略代码（循环、条件、调用感知 API）——表达力超过"选技能"，处理"把积木摆成笑脸"这类组合任务
- **PaLM-E**：把接地做进模型——多模态 token（图像+状态）直接进 LLM，规划器自己"看得见"
- **终局形态：快慢双系统**（2025-2026 主流）：慢系统 VLM 做理解与子任务规划（~Hz 级），快系统 VLA/控制器做执行（~百 Hz），π0.5 的高低层、GR00T 的 System2/1、Figure Helix 全是这个板式——M4.5 VLM 到 VLA 专题的"分层 vs 端到端"之争，答案是**分层回来了，但接口从离散技能库变成了潜向量/子任务语言**

## 四、批判（复试杀手锏）

1. **技能库天花板**（SayCan 硬伤）：只能组合已有技能，技能库没有"拧瓶盖"就永远拧不了——规划再聪明也救不了执行贫穷；这正是 VLA 要扩充的"词汇量"
2. **错误恢复依然稚嫩**：闭环重规划能发现"抓空了"，但"杯子倒了水洒了"这种连锁后果的收拾，当前系统基本不会
3. **延迟税**：每步过一遍大模型，实时性差；快慢分层是妥协而非根治——接口信息瓶颈（M4.6 跨本体专题 Q2 呼应）
4. **评测又是重灾区**：长时序任务成功率=各步成功率连乘，10 步任务每步 95% 也只剩 60%——demo 里的"全程丝滑"要打问号（M6.2 评测危机专题工具再次上岗）

## 五、复试级问答

**Q1：什么是 grounding 问题？SayCan 怎么解？**
要点：语言知识不接物理现实（不知道当前状态下什么可行）。SayCan：LLM 语义合理性 × 价值函数物理可行性，乘积选技能。升华：接地的本质是**给语言先验加上状态条件**，后续所有工作（多模态输入、闭环反馈）都是在加强这个条件。

**Q2：LLM Agent 和具身 Agent 的区别，除了"有没有身体"还有什么？**
要点：①动作可靠性——API 调用确定成功 vs 物理动作概率成功，所以具身必须做闭环监控与恢复；②状态可观测性——软件状态可完全读取 vs 物理状态要靠感知估计（有噪声）；③时间性——软件可暂停重试 vs 物理世界实时流逝（拿着的杯子不能"暂停"）。答出三条，秒杀只会说"有身体"的竞争者。

**Q3：快慢双系统会是终局吗？**
开放题参考：支持——生物学同构（人也是皮层慢规划+小脑快控制）、工程上频率/参数量矛盾的自然解；质疑——接口是人为设计的信息瓶颈，端到端派认为算力上来后单一大模型直接出高频动作（"苦涩教训"逻辑）。稳妥结论：中期分层实用主义胜出，长期取决于算力与数据曲线——展现你懂两边论据。

## 工程视角附录

**SayCan 打分循环的实现细节**：

SayCan 对候选技能 $k\in\mathcal{K}$ 使用

$$
k^*=\arg\max_{k\in\mathcal{K}}
p_{\mathrm{say}}(k\mid l,h)\,
p_{\mathrm{can}}(k\mid o),
$$

把语言模型给出的任务相关性与价值函数估计的可执行性相乘。

```python
for skill in skill_library:                      # ["拿海绵", "去桌边", ...]
    # Say: 不是让 LLM 生成回答，是取候选文本的 token 概率！
    p_say = LLM.logprob(f"任务:{task} 下一步:{skill.text}")
    p_can = value_net[skill](camera_obs)         # 每个技能一个价值网络
    score[skill] = p_say * p_can
execute(argmax(score)); observe(); replan()      # 闭环
```

**现代快慢双系统的接口长相**（2026 主流板式）：

```python
# 慢系统 ~1Hz：VLM 规划器
plan = vlm(image, task)      # → {"subtask": "pick up the sponge", "done": false}
# 快系统 ~50Hz：VLA 执行器
action_chunk = vla(image, plan.subtask)
# 重规划触发：子任务完成 / 超时 / 执行器报异常
```

**常见坑**：
1. Say 分数用"生成式问答再解析"代替 token 概率 → 不稳定且慢；用 logprob
2. Can 校准是命门：价值网络过于自信（没见过的状态也打高分），乘积直接失效——需要校准或保守估计
3. 重规划频率两难：每步重规划=慢+抖，出错才重规划=错误已传播；工程折中是"子任务边界+异常触发"
4. 长时序任务 debug：先录全程日志（每步的 plan/subtask/action），90% 的失败是规划-执行接口上的语义漂移（规划器说"杯子"，执行器看到两个杯子）
