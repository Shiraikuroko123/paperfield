## 12.1 先看四个旋钮互相“串线”

一次实验把 group size 从 $8$ 改成 $32$，同时因为显存增加把 batch prompt 数减半；reward 看似上升，但其实每次更新看到的题目更少。再把 generation length 从 $2048$ 改成 $4096$，若每条回答仍除以自己的长度，原有 token 的单项权重会下降，整体梯度范数也可能明显变化。若只记住某篇论文的 `G=16, lr=1e-6`，很容易把这些耦合误认为普适定律。

本章目标是建立一个可复现的调参实验：固定总 rollout token 预算，每次只改变一个因素，记录它影响的是方差、样本覆盖、策略漂移还是截断偏差。

## 12.2 Group size $G$：先算“没有信号”的概率

对二值 reward，单条回答成功概率为 $q$。一个 group 完全成功或完全失败时，中心化 reward 没有区分度。若样本近似独立，zero-variance 概率是

$$
P_{\mathrm{zero}}
=q^G+(1-q)^G.
$$

例如 $q=0.5$：

- $G=2$ 时，$P_{\mathrm{zero}}=0.5$；
- $G=8$ 时，$P_{\mathrm{zero}}=2/256\approx0.0078$。

增大 $G$ 通常让组内比较更有机会出现成功/失败混合，但不是无条件更好：固定 rollout token 预算下，$G$ 越大，每次 update 覆盖的不同 prompt 越少，prompt-level 方差可能上升，生成成本也线性增加。

**工程记录：** `zero_variance_group_rate`、有效 group 数、unique prompt 数、每 prompt 平均 token 和 reward 分布，而不是只记最终准确率。实验起点可以在 $G\in\{4,8,16\}$ 做小网格；论文中出现 $16$ 或 $64$ 不代表你的任务应照抄。

## 12.3 固定预算时的 trade-off

设总 rollout token 预算为 $B_{\mathrm{tok}}$，平均每条回答长度为 $T$，则大致能覆盖的 prompt 数为

$$
B_{\mathrm{prompt}}
\approx\frac{B_{\mathrm{tok}}}{G T}.
$$

每个变量的意义很直接：增加 $G$ 或 $T$，在同样 token 预算下就减少不同 prompt 的数量。调参时应比较相同 $B_{\mathrm{tok}}$，否则“更大的 G 更好”可能只是花了更多生成钱。

## 12.4 Learning rate：先用 KL 和梯度判断，不背固定数

policy gradient 更新近似为

$$
\theta_{\mathrm{new}}
=\theta_{\mathrm{old}}-\alpha g,
$$

其中 $\alpha$ 是 learning rate，$g$ 的大小又受 reward scale、advantage normalization、token denominator、world size 和 batch token 数影响。

因此同一个 $\alpha$ 在以下变化后不再等价：

- reward 整体乘了 $10$；
- 从 sequence mean 改成 token mean；
- group std normalization 开关改变；
- global batch token 数或梯度累积步数改变；
- LoRA 和全参参数的梯度尺度不同。

更稳妥的流程：先用小学习率跑几十个 update，记录 approximate KL、clip fraction、entropy、梯度范数和 reward；若单步 KL 突然超预算，按 log scale 降低 learning rate；若所有 ratio 都靠近 $1$ 且 reward 没有信号，再逐步提高。这个过程是经验校准，不是理论保证。

## 12.5 PPO epoch：重用数据也重用偏差

把一批 rollout 切成 minibatch。所有 minibatch 走一遍叫一个 epoch；如果有 $M$ 个 minibatch，走 $M$ 次不等于 $M$ 个 epoch。

在一个 PPO epoch 内应固定：

- 行为策略 old log-prob；
- reward 和 advantage；
- response mask 和 finish reason。

每个 epoch 只重算当前 policy log-prob。重复 epoch 的收益是提高样本利用率，代价是 policy 离 behavior 越来越远、ratio 和 verifier 噪声被重复放大。对昂贵长 CoT，先从 $1$ epoch 开始；只有 KL、clip fraction 和 ratio 分位数都稳定，才尝试 $2$ 或更多。

## 12.6 Generation length：上限、截断和 EOS 是三个变量

`max_new_tokens` 是硬上限，不是模型应达到的目标长度。必须分别记录：

- 正常 EOS 结束；
- 达到长度上限的截断；
- 环境超时或工具失败。

设正确答案需要 $T^*=3000$ token，而上限只有 $2048$，即使策略本来能解也会被截断。反过来，上限从 $2048$ 加到 $8192$ 可能产生长尾 rollout，使 p99 延迟和显存峰值爆炸。

EOS 是否进入 response loss 也要固定：不训练 EOS，模型可能学不会停止；把截断 token 当作普通负样本，又可能把“没来得及写完”与“推理错误”混为一谈。可为 overlong 轨迹设置单独 shaping 或 mask，但要与任务成功做消融。

## 12.7 四个旋钮如何联动

| 旋钮 | 主要影响 | 典型观测 |
|---|---|---|
| $G$ | 组内 baseline 方差、prompt 覆盖、rollout 成本 | zero-variance、unique prompts、advantage std |
| learning rate | 每步 policy drift、梯度噪声 | KL、ratio p99、entropy、grad norm |
| PPO epoch | 数据复用率与 staleness | 每 epoch ratio、clip fraction、ESS |
| generation length | 截断偏差、长尾成本、长度偏好 | finish reason、p50/p95/p99、tokens per success |

不要同时大改四个变量。否则即使 reward 变化，也无法知道是哪一项造成的。

## 12.8 一个可复现的起始实验

以下只是实验起点，不是定律：

```text
group_size = 8
ppo_epochs = 1
固定 temperature 与 top-p
使用全局有效 response token 作为 batch 统计单位
每次 update 记录 KL、clip fraction、entropy、zero-variance group、长度 p50/p95/p99
```

先保持总 rollout token 预算不变，分别只改变 $G$、学习率、epoch、长度上限。用相同 prompt 集、verifier 版本和随机种子配对比较。

## 12.9 调参实验矩阵

第一轮可用对数或小离散网格：

| 实验 | 只改变的变量 | 示例候选 | 固定内容 |
|---|---|---|---|
| A | $G$ | $4,8,16$ | 总 rollout token、epoch、LR |
| B | LR | $0.5\times,1\times,2\times$ 基准 | $G$、长度、epoch |
| C | PPO epoch | $1,2,4$ | 总 rollout、LR、clip 区间 |
| D | length cap | 任务长度分位数附近的 3 个值 | 其他设置 |

每个实验至少重复两个 seed，并报告置信区间或 seed 间范围。单次 reward 曲线不能支撑“最佳超参”结论。

## 12.10 调参伪代码

```python
for update in range(num_updates):
    batch = rollout(
        policy=policy,
        group_size=config.group_size,
        max_new_tokens=config.max_new_tokens,
        temperature=config.temperature,
        top_p=config.top_p,
    )
    batch.advantages = compute_group_advantages(
        batch.rewards,
        batch.group_ids,
        normalize_std=config.normalize_std,
    ).detach()

    for epoch in range(config.ppo_epochs):
        for minibatch in split_by_tokens(batch):
            loss, stats = ppo_loss(policy, minibatch)
            optimizer.zero_grad(set_to_none=True)
            loss.backward()
            clip_grad_norm_(policy.parameters(), config.max_grad_norm)
            optimizer.step()
            logger.log({"update": update, "epoch": epoch, **stats})

    # 发现 KL 或 p99 ratio 越界时，按规则降低 LR 或提前结束 epoch。
    if stats["approx_kl"] > config.kl_budget:
        scheduler.reduce_lr(factor=0.5)
```

生产系统还要按 token 数而不是样本数切 minibatch，避免长回答让显存和梯度突然变化；上面的 `split_by_tokens` 是一个需要单独测试的组件。

## 12.11 项目实验与完成标准

选择一个有可靠 verifier 的任务，固定总 rollout token 预算和训练步数，运行 A--D 四组实验。每组报告：

- pass@$1$ 与 pass@$k$；
- reward 分量与独立 verifier；
- ratio p50/p99、approx KL、clip fraction、ESS；
- zero-variance group rate；
- finish reason、长度分位数、tokens per successful answer；
- 墙钟时间、GPU 利用率和峰值显存。

完成标准是你能对每个改动给出因果解释，例如“$G$ 增大降低了 zero-variance，但 unique prompt 数下降”；而不是只说“这个配置 reward 最高”。
