## 11.1 先看一个只在 rollout 失败的模型

同一个 checkpoint 在训练 forward 上，某个 prefix 的下一个 token log-prob 是 $-0.20$；把权重同步到推理引擎后，log-prob 变成 $-0.65$，生成结果也不同。dense 模型可能只有小的 kernel 误差，MoE 还要决定每个 token 发送给哪个 expert；一个边界 token 路由改变，后续 hidden state 就可能完全不同。

本章目标不是背某个“神奇一致性算法”，而是建立可定位的因果链：router logits → top-$k$ expert set → capacity/dispatch → expert 输出 → lm logits → sampling distribution。每一层都要能打印和比较。

## 11.2 MoE 一次前向做了什么

对 token hidden state $h_t$，router 产生 expert 分数：

$$
z_t=W_rh_t,
\qquad
p_t=\operatorname{softmax}(z_t).
$$

$W_r$ 是 router 参数，$p_t(e)$ 是 token 被送到 expert $e$ 的概率。若使用 top-$K$ 路由，选择集合是

$$
\mathcal E_t=\operatorname{TopK}(p_t,K).
$$

在选中的 expert 内重新归一化权重，输出可抽象写成

$$
h'_t=\sum_{e\in\mathcal E_t}
\widetilde p_t(e)\,f_e(h_t),
$$

其中 $f_e$ 是第 $e$ 个 FFN，$\widetilde p_t$ 是选中集合内的 gate 权重。只要 $\mathcal E_t$ 或 gate 权重不同，$h'_t$ 就可能不同。

## 11.3 为什么训练和推理容易走不同路

**容量（capacity）。** 训练为了固定通信和显存，常给每个 expert 一个 token capacity；超出的 token 可能被丢弃、补到别处或用 residual。推理通常希望 dropless。于是同一个 batch 中“和谁一起出现”会改变路由结果。

**数值与 tie-break。** BF16、FP8、FP32 的 softmax 累加不同；两个 expert 分数接近时，舍入或 top-$k$ 相同分数的 tie-break 会改变集合。

**router noise。** 训练为探索或负载均衡加入噪声，推理关闭噪声；如果 rollout 引擎又有不同的噪声策略，行为分布就不再是训练 forward 的分布。

**batch-dependent dispatch。** 动态 packing、padding、all-to-all 顺序和 expert capacity 让一个 token 的处理结果依赖同批其他 token。

**kernel/版本/权重。** Megatron-Core fused MoE、vLLM/SGLang kernel、checkpoint 转换、router bias、expert parallel rank 映射任何一处不一致，都会反映到 log-prob。

## 11.4 先做一个边界 top-$k$ 数值例子

两个 expert 的 router logits 为 $(1.0000,0.9999)$，使用 top-$1$。FP32 下第一个可能胜出；若低精度舍入后都变成 $1.00$，tie-break 可能选择第二个。假设两个 expert 输出分别为 $f_1(h)=2$、$f_2(h)=-2$，则路由差异使 hidden 输出相差 $4$，远大于原始 $0.0001$ 的 logits 差。

这个例子说明：不能只比较最终 reward 来推断“MoE 训推不一致”；应先统计每层 top-$k$ agreement，再逐层追踪数值误差。

## 11.5 对 importance sampling 的真正影响

如果 rollout 记录的是实际行为分布 $\mu$ 的 old log-prob，训练时正确计算当前策略 $\pi_\theta$ 的 log-prob，那么 ratio

$$
\rho_t=\frac{\pi_\theta(a_t\mid s_t)}{\mu(a_t\mid s_t)}
$$

在数学上仍有定义，即使训练和推理的内部路由不同。真正危险的是：

- rollout 实际用的是一个分布，却用训练引擎重算的 log-prob冒充 $\mu$；
- support 因 top-$k$/top-$p$ 截断不覆盖；
- 路由差异让 $\rho_t$ 方差很大、clip fraction 和 KL 失控；
- old snapshot 与当前权重版本错配。

因此“训推不一致会让 IS 数学彻底失效”太绝对；它首先使 behavior denominator 记录和 ratio 稳定性变得危险。

## 11.6 解决方案按层次排查

| 层次 | 做法 | 代价 |
|---|---|---|
| 路由规则 | 统一 top-$K$、tie-break、router noise、capacity 语义 | 可能降低吞吐或负载均衡 |
| 精度/kernel | rollout 与 trainer 使用同一 forward；或逐 token 校准 log-prob | 引擎耦合、速度下降 |
| 权重版本 | 每条样本保存 checkpoint hash、policy version、router 配置 | stale 样本被丢弃 |
| 路由重放 | rollout 记录 top-$K$ expert mask，trainer 重放集合内路由 | 额外存储和通信；不修复 lm-head 差异 |
| 目标函数 | GSPO/CISPO/DPPO 等降低 token ratio 噪声或直接约束 divergence | 引入估计偏差和复杂度 |
| 监控 | route agreement、delta-logp、expert load、drop rate、ratio 分位数 | 需要埋点和回放工具 |

R3 或 Keep Routing 一类方法通常只重放 expert selection mask，并允许集合内的 gate 仍由当前 router 计算；它们减少 selection mismatch，但不会自动解决 sampling mask、权重同步或低精度 lm-head 的差异。

## 11.7 逐层诊断流程

固定一个 prompt、一个随机 seed 和一个 checkpoint，执行以下顺序：

1. 比较每层 router logits 的最大绝对误差；
2. 比较 top-$K$ expert 集合的 Jaccard agreement；
3. 比较每个 expert 收到的 token 数、drop/overflow 数；
4. 比较 expert 输出 $h'_t$ 的误差；
5. 比较 lm-head logits 和被选 token 的 log-prob；
6. 最后才比较生成 token 与最终 reward。

如果只在大 batch 出现，优先查 capacity、packing 和 all-to-all；如果单 token 也出现，优先查精度、权重和 kernel；如果 top-$K$ 一致但 log-prob 不同，查 gate 权重、expert 输出和 lm-head。

## 11.8 对齐 harness 伪代码

```python
def compare_engines(prompt, checkpoint):
    train_trace = trainer.forward_with_trace(prompt, checkpoint)
    serve_trace = rollout_engine.forward_with_trace(prompt, checkpoint)

    metrics = {
        "router_max_abs": max_abs(
            train_trace.router_logits,
            serve_trace.router_logits,
        ),
        "route_agreement": topk_agreement(
            train_trace.expert_ids,
            serve_trace.expert_ids,
        ),
        "hidden_max_abs": max_abs(
            train_trace.moe_outputs,
            serve_trace.moe_outputs,
        ),
        "logit_max_abs": max_abs(
            train_trace.logits,
            serve_trace.logits,
        ),
        "selected_logp_delta": selected_logp_delta(
            train_trace, serve_trace,
        ),
    }
    return metrics
```

要保存的是每层摘要和少量可回放 token，不要默认保存整个 batch 的所有 hidden state。对齐 harness 应在每次 kernel、精度或 checkpoint 转换变更后运行。

## 11.9 项目实验与完成标准

用一个两层、四 expert 的 toy MoE，分别开启/关闭 capacity、router noise、BF16 和动态 batch。对同一批 prefix 比较 dense reference、训练引擎和 rollout 引擎：

- top-$K$ agreement；
- expert load coefficient of variation；
- token drop rate；
- selected log-prob 的均值和 p99 差异；
- 最终生成差异。

完成标准是你能定位“差异第一次出现在哪一层”，而不是只说“MoE 需要保持一致”。此外要能解释路由重放减少了什么、没有减少什么。
