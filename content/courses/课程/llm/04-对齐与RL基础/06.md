## 6.1 先看两个“都变强了”的模型

模型 A 训练了更多 RL，单次回答正确率从 $40\%$ 变成 $60\%$；模型 B 参数没变，但每道题采样 $32$ 次并用 verifier 选最好，最终正确率也达到 $85\%$。这两个数字不能直接说明谁的推理能力更强：A 把计算花在训练期，B 把计算花在每次请求。

本章项目要画出同一模型在不同计算预算下的曲线，区分：

- 训练阶段改变参数分布的 exploration；
- 测试时不改参数、重复搜索候选的 exploration；
- 两者如何互相提供数据。

## 6.2 RL training 的探索对象

RL 训练时，策略本身是一个分布 $\pi_\theta$。探索通常来自：

1. sampling temperature 或 entropy bonus；
2. 同一 prompt 的多个 group 样本；
3. 任务混合、难度 curriculum 和新 prompt；
4. Agent 环境的随机转移与不同工具路径；
5. 参数更新后进入新的行为区域。

如果策略变成几乎确定性分布，某个正确但低概率的路径再也采不到，后续 RL 也无法把它学上来，这就是 exploration collapse。

## 6.3 Test-time scaling 的探索对象

测试时 scaling（TTS）不更新 $\theta$，而是为一个固定输入多花计算：

- 独立采样 $N$ 个答案；
- best-of-$N$，由 reward model 或 verifier 选择；
- majority vote / self-consistency；
- tree search、MCTS、beam-like search；
- 先生成多个计划，再逐个执行工具。

它探索的是**当前模型已经赋予非零概率的候选空间**。如果正确解的概率严格为 $0$，再多测试时计算也找不到；如果答案高度相关，增加 $N$ 的收益会远低于独立样本公式。

## 6.4 pass@$k$ 的一步推导

假设单次采样正确概率是 $p$，并且 $k$ 次采样相互独立。全部失败的概率是

$$
P(\text{all fail})=(1-p)^k.
$$

至少一次成功的概率因此为

$$
\operatorname{pass@}k=1-(1-p)^k.
$$

例如 $p=0.4$：

$$
\operatorname{pass@}1=0.4,
\quad
\operatorname{pass@}4=1-0.6^4\approx0.8704.
$$

这是独立采样基线，不是现实保证。若两次采样完全相同，实际 pass@$4$ 仍只有 $0.4$；若候选之间有负相关，收益可能高于独立公式。

## 6.5 为什么 pass@k 有时看起来“反常”

在固定 prompt、固定采样分布且真实单次成功率 $p$ 上升时，独立公式中的 pass@$k$ 必然不下降。实证中看到 top-1 上升而 pass@$k$ 下降，通常是指标条件变了：

1. top-1 用 greedy，pass@$k$ 用 temperature sampling；
2. 训练改变了 sampling temperature、top-$p$ 或 EOS 分布；
3. 跨 prompt 先平均 $p$ 再套公式，和逐题算 pass@$k$ 不同；
4. 候选相关性或 verifier 选择偏差改变；
5. 样本量小，估计误差大。

因此报告时应固定 prompt 集、解码设置和 verifier，并同时给出 pass@$1,4,16,64$、候选多样性和平均 token 成本。

## 6.6 训练与 TTS 的互补闭环

一个实用流程是：

1. TTS 找出“模型偶尔能做对”的题，保存成功轨迹和失败类型；
2. 用这些轨迹做 RFT、SFT 或在线 RL，提高正确路径的概率；
3. 训练后重新测不同 $k$，看能力是 top-1 提升，还是只在高预算下提升；
4. 若 pass@$64$ 上升而 pass@$1$ 不变，说明模型有潜在能力但没有学会稳定选择；若 pass@$1$ 上升而候选多样性塌缩，继续放大 $k$ 的收益可能变差。

“能力边界”要按预算定义。一个模型在 $k=1$ 做不到，不代表它在 $k=64$ 没有正确轨迹；反过来，TTS 选不出来也可能是 verifier 不可靠，而不是模型没有解。

## 6.7 一个小数字预算账本

设一次采样平均 $100$ token，GPU 每秒生成 $1000$ token。

- RL training：每轮生成 $10^6$ token，训练一次，之后所有用户请求都受益；
- TTS：每个用户问题采样 $16$ 次，即每问 $1600$ token，延迟和成本都乘约 $16$。

若用户请求量很大，训练期成本可能更划算；若题目一次性、分布会快速变化，TTS 更灵活。不能只比较准确率，要画“正确率--生成 token--墙钟延迟”的 Pareto 曲线。

## 6.8 多样性不是简单的熵

策略熵为

$$
H(\pi(\cdot\mid s))
=-\sum_a\pi(a\mid s)\log\pi(a\mid s).
$$

熵高表示分布更分散，但分散到无用乱码也不算有效探索。对 LLM 更应记录：

- 不同答案的 n-gram 或语义相似度；
- verifier 失败类型是否覆盖不同模式；
- 候选的 unique final answer 比例；
- 成功答案之间的路径多样性。

## 6.9 训练和 TTS 对应的伪代码

```python
def test_time_scale(prompt, k):
    candidates = [policy.generate(prompt, temperature=0.7)
                  for _ in range(k)]
    scores = [verifier(c) for c in candidates]  # continuous diagnostic scores
    successes = [is_correct(c) for c in candidates]  # binary pass/fail
    return candidates[argmax(scores)], {
        "k": k,
        "pass_at_k": any(successes),
        "best_score": max(scores),
        "unique": len(set(candidates)),
    }

for batch in training_loader:
    # group exploration：同一 prompt 生成多个候选。
    groups = rollout_group(policy, batch.prompts, group_size=G)
    rewards = verifier(groups.answers)
    advantages = group_baseline(rewards).detach()
    loss = policy_gradient_loss(groups, advantages)
    optimizer.step(loss)
```

训练循环中，`groups` 的候选会反过来改变参数；TTS 函数只返回答案，不调用 `optimizer.step`。这就是两者最基本的边界。

## 6.10 项目实验与完成标准

选一个有可靠 verifier 的小任务，固定模型 checkpoint，测 $k=1,2,4,8,16,32$。再训练一个小 RL 版本，重复同一测试。记录：

1. pass@$k$；
2. 每题候选相似度；
3. verifier 选择错误率；
4. 每个成功答案的 token 成本和延迟；
5. 训练前后 reward 分布的尾部。

完成标准：你能用数据回答“RL 是提高单样本概率还是仅仅制造更多候选”“TTS 失败是 support 不足还是选择器不准”“增加训练计算和增加请求时计算的成本曲线如何不同”。
