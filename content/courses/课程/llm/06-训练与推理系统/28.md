## 28.0 先看一个看似合理的想法

一条 agent 轨迹已经生成了 2,000 个 token，训练器刚好更新了一次权重。为了省时间，有人会说：“把之前的 KV cache 留着，换上新权重继续生成即可。”这个想法在数学上通常不成立：KV 是由**旧权重和旧 prefix 一起算出的激活**，不是 token id 的永久缓存。

## 28.1 一个数字例子

假设同一个 prefix 在旧 policy 下某层产生 key 向量 $k_{old}=[1.00,0.50]$，新权重产生 $k_{new}=[1.02,0.48]$。query 是 $q=[0.8,0.6]$，attention score（忽略缩放）分别为

$$
q\cdot k_{old}=1.10,
\qquad
q\cdot k_{new}=1.104.
$$

一次看差别只有 0.004；但经过多层 softmax、残差和上千个 token 后，最终下一个 token 的 log-prob 可能累积成可测的差异。更重要的是，旧 KV 与新层的 hidden state 不再来自同一计算图，所以不能声称“这是新 policy 的精确 forward”。

## 28.2 什么时候可以复用

- **同一个 policy snapshot 继续生成：** 可以保留 prefix KV。partial rollout 只是暂停请求，保存 token 位置、随机采样状态和 cache block。
- **policy 已更新：** 旧 KV 只能表示旧 behavior policy 的状态。若想继续用新 policy，需要重算受影响的 prefix，或者放弃旧 KV，从 token id 重新 prefill。
- **只做数据存档：** 保存 token prefix、每 token old log-prob、finish state 和 sampling metadata，通常比保存所有 KV 更小，也更容易回放。

把“继续旧 policy 的生成”和“用新 policy 计算概率”分成两个函数，能避免概念混乱：

```python
if request.policy_version == current_policy_version:
    response = decode_with_existing_kv(request.kv)
else:
    # old KV is still valid only as behavior evidence, not as new forward state
    prefix = request.tokens
    response = prefill_and_decode(current_policy, prefix)
```

## 28.3 partial rollout 的数据结构

中断点至少要保存：

```text
trajectory_id, segment_id, policy_version
prefix token ids, response token ids, position offset
finish_reason, environment/tool state, RNG/sampling metadata
old_logp per token, loss mask, reward attribution status
```

如果一条轨迹由旧版本 segment 1 和新版本 segment 2 组成，行为概率应按 segment 拆开：

$$
\log\mu(y\mid x)=
\sum_{j=1}^{J}\sum_{t\in T_j}
\log\mu_{v_j}(y_t\mid s_t).
$$

这里 $j$ 是 segment 编号，$T_j$ 是该段包含的 token 索引集合，$v_j$ 是该段的 behavior policy version，$s_t$ 仍表示生成到 token $t$ 前的状态/前缀。不能把 segment 集合和状态符号都写成 $s$，也不能把它们拼成一个版本号再计算单一 ratio。

## 28.4 最小实验：旧 KV 误差有多大

选一个小模型和固定 prefix。保存旧版本的 KV，然后做三次下一 token 计算：

1. 旧权重 + 旧 KV（基准）；
2. 新权重 + 重新 prefill（正确的新 policy）；
3. 新权重 + 旧 KV（错误复用）。

记录三组 logits 的最大绝对差、选中 token 的 `delta_logp`、KL 和最终 reward：

```python
delta = (logits_new_recompute - logits_new_old_kv).abs().max()
token_kl = (p_new_recompute *
            (p_new_recompute.log() - p_new_old_kv.log())).sum()
```

把 prefix 长度从 128 增加到 4,096，观察误差是否随长度增大。若只在低精度或量化 kernel 下出现差异，也不能据此宣布“跨版本 KV 安全”；应明确允许的近似误差和训练目标是否能容忍它。

## 28.5 AReaL 与其他实现的边界

AReaL 的 interruptible generation 思路是：权重更新时中断 in-flight 请求，丢弃旧 KV，用新权重重算 prefix 后继续。这样做牺牲一部分已做计算，换来版本边界清晰；一条轨迹可能有多个 behavior segment，所以要保留每段的 log-prob。slime 的 partial-rollout 行为随 commit 和示例变化，有的路径 abort 后 requeue/restart，有的允许更细粒度调度；必须查当前版本代码，不能笼统写成“所有框架都能恢复旧 KV”。

## 28.6 验收与追问

**验收：** 你能用一句话解释“KV 依赖权重”，能画出同版本 resume 与跨版本 restart 的两条路径，并通过三次 logits 对比实验量化旧 KV 误差。

追问：如果不能保存完整 old log-prob，能否只保存 sequence log-prob？这会失去 token-level ratio 的诊断和 clip，通常不适合 PPO；GSPO 等 sequence-level estimator 可以改变粒度，但仍要知道 behavior probability 的定义。
