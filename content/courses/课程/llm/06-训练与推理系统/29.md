## 29.0 先看一个反直觉现象

一个 MoE 层有 64 个 expert，每个 token 只路由到 top-2。按“只算两个 expert”的直觉，应该比 dense FFN 快很多；但小 batch 的 decode 反而更慢。原因是每个 token 还要经历 dispatch、all-to-all、combine，而且每个 expert 收到的 token 太少，GEMM 变成许多小矩阵。

## 29.1 一条 token 的路径

```text
hidden states
  -> router 得到 top-k expert index
  -> EP all-to-all dispatch
  -> 每张卡执行本地 expert GEMM
  -> all-to-all combine 回原 token 顺序
  -> 加权合并输出
```

若一次 EP collective 在所有 rank 上合计有 $N$ 个 token、top-$k$ 为 $k$、hidden size 为 $H$、元素大小为 $b$ 字节，dispatch 和 combine 的**全局逻辑 payload 上界**约为

$$
M_{comm}\approx2NkHb.
$$

第一个 2 表示 dispatch 和 combine 来回两次。这里的 $N$ 是整个 EP group 的 token 总数，不是每张卡各有 1,024 个 token。例子：$N=1{,}024$、$k=2$、$H=4{,}096$、BF16（$b=2$）时，单层约

$$
2\times1024\times2\times4096\times2
\approx32\ \text{MiB}
$$

的全局逻辑 token payload，还未计 padding、index 和 NCCL 协议开销，也暂时把所有 top-$k$ 路由都当成需要跨 rank。真实网络字节还要乘“目标 expert 不在本 rank”的比例；本地命中的 token 不走网络，而每个 rank/link 看到的字节又受 EP world size、拓扑和路由偏斜影响。因此 32 MiB 不能直接解释成“每张 GPU 都发送 32 MiB”。decode 若一次只有几十个 token，这笔固定通信很难摊薄。

## 29.2 用一个时间模型定位瓶颈

粗略把一个 MoE step 写成

$$
T_{step}\approx
\max(T_{expert\_compute},T_{alltoall})
+T_{imbalance}+T_{launch}.
$$

`max` 表示理想的计算/通信重叠；现实中若 stream 依赖不允许重叠，就更接近两者相加。$T_{imbalance}$ 来自 expert 负载不均，$T_{launch}$ 来自许多小 kernel。

## 29.3 需要先量的指标

对每个 expert 记录 token count，计算均值、最大值和变异系数：

$$
CV=\frac{\text{std}(n_e)}{\text{mean}(n_e)+\delta}.
$$

同时记录 capacity overflow/drop rate、每个 GEMM 的矩阵形状、dispatch/combine bytes 和 all-to-all 时间。若 $CV$ 很大，先修路由平衡；若 $CV$ 不大但 all-to-all 占 60%，优先修拓扑或通信重叠。

## 29.4 最小实验：batch 与 EP 的交叉曲线

在固定模型上选择 EP=1、2、4，token 数选择 64、256、1,024、4,096。每个点跑足够多轮，记录：

```text
tokens/s, alltoall_ms, expert_gemm_ms, launch_ms
expert_count_mean/std/max, overflow_rate
```

预期小 token 数时 EP=1 可能最快；token 数大到足以形成大 GEMM 后，EP 才可能获益。把不同 policy version 的 response 混在一个动态 batch 会改变 router 和 capacity 行为，测量时要先固定版本。

## 29.5 优化顺序

1. **路由平衡：** router bias、aux-loss-free balancing、capacity/dropless 策略；同时检查训练和 rollout 的 route agreement。
2. **拓扑放置：** 高频互通 expert 尽量在同一节点；把高频小消息留在 NVLink，减少跨节点 all-to-all。
3. **kernel 与重叠：** fused dispatcher、token permutation、persistent GEMM；让下一批 dispatch 与当前 expert GEMM 使用不同 stream 并验证依赖。
4. **动态 batch：** length bucketing 和 token packing，但不要为塞满 expert 而跨 policy version 混样本。

## 29.6 EP 对数值的影响

all-to-all 后的 token 排序、浮点归约顺序、router 精度和 expert dropout 都可能改变 logits。吞吐优化完成后必须重新比较训推 `delta_logp`、router top-k 一致率和最终 reward；“速度快了”不等于“RL 信号仍然正确”。

**验收：** 你能从 $2NkHb$ 估算通信量，解释为何小 batch 的稀疏计算可能更慢，并用 expert token count 的 CV 判断下一步该优化路由还是网络。
