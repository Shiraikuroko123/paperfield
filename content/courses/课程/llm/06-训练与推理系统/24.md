## 24.0 serving 现象

静态 batch 中，短请求结束后槽位空着；continuous batching 在每个 decode tick 动态加入/退出请求，通常提高 serving 吞吐。但 RL 还有训练 barrier，serving 利用率提高不等于 optimizer 更快。

## 24.1 RL 的三个不变量

**同一 group 必须同一版本。** 同一 prompt 的 $G$ 条回答要来自同一个 policy snapshot 和 sampler。不能按完成时间跨版本凑 group。

**保存真实 behavior。** 采样器经过 temperature 和 top-$p$/top-$k$ 后的分布为

$$
\mu_t(v|s)=
\frac{\exp(z_v/T)\mathbf 1[v\in S]}
{\sum_{u\in S}\exp(z_u/T)}.
$$

$S$ 是 warper 保留的 support。ratio 分母必须是这个 $\mu_t$，或在训练时做明示校正；原始 softmax 不是同一个分布。

**batch invariance。** 混批可能改变 padding、MoE capacity、fused reduction 顺序。定义

$$
\Delta_{\mathrm{BI}}
=\max_t|\log p_{\mathrm{solo}}(y_t|s_t)
-\log p_{\mathrm{mixed}}(y_t|s_t)|.
$$

在 deterministic 模式和固定 seed 下测它；若超阈值，old-logp 会带系统误差。

## 24.2 vLLM 与 SGLang 的实际比较

两者都支持 paged KV 和 continuous batching，版本在快速变化。vLLM 常见强项是通用高吞吐 serving、PagedAttention、模型/量化生态和广泛 trainer 集成；SGLang 常见强项是程序化生成、Radix/prefix cache、结构化输出、多轮/agent 分支。不要只用旧标签或单一 tokens/s 选型。

RL benchmark 要从 prompt 一直测到 weight update：有效 tokens/s、nonzero-advantage rate、权重同步等待、KV hit/miss、P99、old-logp 一致性、最终 pass@k。

## 24.3 三个常见事故

1. **跨版本组装**：v10 和 v11 的回答混成一个 group，baseline 没有共同 behavior；
2. **warper 丢失**：rollout 用 top-p，trainer 用未截断 softmax 计算 old logp；
3. **cache 错复用**：prefix cache key 不含权重版本或模板 hash，换权重后仍使用旧 KV。

## 24.4 项目：可审计 rollout 记录

~~~json
{
  "prompt_id": "p42",
  "group_id": "p42-v17-g03",
  "policy_version": 17,
  "temperature": 1.0,
  "top_p": 0.95,
  "tokens": [101, 202, 303],
  "old_logp": [-0.7, -1.2, -0.4],
  "finish_reason": "stop",
  "kv_key": "sha256(template|weights|prefix)"
}
~~~

自动测试四项：同组版本和 sampler hash 相同；保存的 old logp 可复算 ratio；权重更新后旧 KV key 不命中；solo/mixed 的 $\Delta_{\mathrm{BI}}$、pass@k 和 expert route 一致率在阈值内。

serving 侧记录 active sequences、KV allocated/used blocks、hit/miss/eviction、queue wait、TTFT、decode tokens/s、P50/P99、weight-sync；`nvidia-smi` 只能做粗粒度辅证。

## 24.5 手算静态 batch 与连续 batch

用一个简化 worker：每个 tick 每条活跃序列生成 1 token。四个请求长度为 $(2,2,2,8)$，静态 batch 要等 8 tick，总有效 token为 14，槽位容量为 $4\times8=32$，理想有效率只有 $14/32=43.75\%$。continuous batching 在第 2 tick 结束三条短请求后立即补入新请求，空槽可继续工作；实际效率取决于队列中是否有可兼容的 prompt、KV block 和同一 policy version。

连续调度不能跨 group 凑样本。举例：`p42-v17-g03` 的前三条已结束，第四条仍在 decode；如果此时把 v18 的回答补进来，服务吞吐增加了，但 group advantage 不再对应同一个 behavior policy。

每个 scheduler tick 保存 `tick_id`、`active_seq`、`admitted_seq`、`finished_seq`、`free_kv_blocks`、`group_id`、`policy_version`、`sampler_hash`、`queue_wait_ms`、`prefill_ms`、`decode_ms`、`weight_sync_ms` 和 `batch_shape`。引擎对比必须同时保存 vLLM/SGLang 版本、backend、TP/EP 配置和 cache policy。

**验收标准**：静态与 continuous 的有效 tokens/s、P99、KV 峰值和训练 step time 都有；同一 group 版本检查为 100% 通过；solo/mixed 的 $\Delta_{\mathrm{BI}}$、old-logp 重算误差和最终 pass@k 在阈值内。<br>
**追问**：continuous batching 为什么不能自动消除 optimizer barrier？vLLM 的 PagedAttention 与 SGLang 的 Radix cache 解决的问题有什么不同？如何用 `sampler_hash` 证明 top-$p$ 参数没有被悄悄改掉？

## 统一的样本记录（Project 25-35 前置）

后文把一次 rollout 记录成下面这组字段：

$$
z_i=(x_i,y_i,R_i,m_i,v_i,\ell_i,c_i).
$$

- $x_i$：输入 prompt；
- $y_i$：模型生成的 response；
- $R_i$：verifier 或 reward model 给的分数；
- $m_i$：只标记 response token 的 mask；
- $v_i$：生成时的 policy version；
- $\ell_i$：生成时实际选中 token 的 log-prob 序列；对精确的 importance correction，应定义为
  $\ell_{i,t}=\log\mu_{i,t}(y_{i,t}\mid s_{i,t})$，其中 $\mu$ 是 temperature、top-$k$/top-$p$ 截断后重新归一化的**实际 behavior 分布**；
- $c_i$：temperature、top-$p$、停止原因以及 sampler/support hash 等采样配置。

$v_i$ 和 $\ell_i$ 不是装饰信息：异步训练时没有它们，就无法知道一条样本究竟来自哪个策略，也无法做 importance correction。若实现另外保存的是 warper 之前的裸模型 log-prob，应单独命名为 `model_logp`，不能冒充 behavior log-prob；仅凭 sampler 配置和 token id 不能从零恢复被截断后的归一化常数。下面的“项目”都应把这些字段写入日志。
