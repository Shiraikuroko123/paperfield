## 32.0 先看两个团队的同一张时间线

假设一次 update 中，rollout 需要 40 秒，trainer 需要 12 秒，权重同步需要 3 秒。同步方案每轮约 55 秒；即使 trainer 只忙 12 秒，剩下时间也在等生成。AReaL 和 slime 都能减少这类浪费，但它们的“主问题”不完全相同：AReaL 更强调 generation/training 解耦和 stale 控制，slime 更强调把 SGLang rollout、Megatron trainer、KV/prefix 与自定义 agent 数据流接成高性能系统。

## 32.1 两种视角

可以用两个问题区分它们：

1. **AReaL 的问题：** 如何让 learner 不被长尾 rollout 的 barrier 卡住，同时仍能处理行为策略与当前策略不一致？
2. **slime 的问题：** 如何在已有 Megatron/SGLang 集群上，把生成、数据 buffer、并行训练和权重同步做成可替换的执行路线？

这不是“一个异步、一个同步”的二分。AReaL 也有工程控制面，slime 也提供 sync、async、fully-async、partial rollout 等路径；要看具体版本的 execution model。

> **版本边界（截至 2026-07-18）：** AReaL 官方仓库在 2026-07-01 发布了 `v2.0.0`（commit `fee938e`），把 training、inference、agent、weight update 等能力拆成独立微服务；配套报告为 arXiv:2607.01120。本章的三策略公式和 staleness 直觉主要来自 2025 报告及通用 actor--learner 原理，不代表 v2 的某个 API 或默认 recipe。复现实验时应同时写明论文版本、仓库 tag/commit 和配置文件路径。

## 32.2 为什么 decoupled PPO 需要三份策略

在完全同步 PPO 中，生成策略和 proximal anchor 往往接近；异步时至少要区分：

- $\pi_{beh}$：真正生成样本的 behavior policy；
- $\pi_{prox}$：最近一次更新前的 proximal anchor，用来限制新策略跳太远；
- $\pi_\theta$：当前要优化的 learner policy。

下面先写一个**逐 token**的概念性目标；$m_{i,t}$ 是 response mask，$A_{i,t}$ 是 advantage，外层 behavior-to-prox 权重不参与反向：

$$
L=-\mathbb{E}_{\tau\sim\pi_{beh}}
\left[
\frac{\sum_t m_t\,\operatorname{sg}(w_t)
\min\left(r_tA_t,
\operatorname{clip}(r_t,1-\epsilon,1+\epsilon)A_t\right)}
{\sum_t m_t}
\right],
\quad
w_t=\exp(\log\pi_{prox}-\log\pi_{beh}),
\quad
r_t=\exp(\log\pi_\theta-\log\pi_{prox}).
$$

最外层 $w_t$ 把行为分布校正到 proximal 分布，内层 $r_t$ 和 clip 把 trust-region 中心放在 proximal policy；$\operatorname{sg}$ 表示 stop-gradient，实际实现还应把 $\pi_{beh}$、$\pi_{prox}$ 的 log-prob 和 $A_t$ 都 detach/freeze，只有 $\pi_\theta$ 接收梯度。若实现采用 sequence-level estimator，就要把 token 求和换成明确的 sequence log-prob/长度归一化，不能把 token ratio 和 sequence ratio 混在一个公式里。实际代码还要处理 staleness 上限、support 截断和全局 reducer；公式不能脱离代码版本直接当作通用 recipe。

## 32.3 slime 的工程数据流

典型路径如下：

```text
prompt/custom data
  -> SGLang rollout（policy version）
  -> verifier / tool / reward
  -> Data Buffer（tokens, masks, scores, versions）
  -> trainer 重算 log-prob、计算 advantage
  -> Megatron forward/backward（DP/TP/PP/EP）
  -> optimizer step
  -> 分片权重或 delta 同步回 rollout
```

slime 的重点不只是“把两个进程接起来”，而是让 Data Buffer 能携带 partial trajectory、agent tool state、版本和自定义 loss 所需的字段。组件越强，接口和版本维护成本也越高。

## 32.4 最小对比实验

用同一模型、同一 prompt 集、同一 reward，跑三个执行模式：sync、async、fully-async。每种模式都记录：

```text
update wall time, rollout/trainer overlap
queue depth, policy-version lag, ratio p99, KL
有效 token/s, reward, clip fraction, dropped samples
```

若 async token/s 增加但 reward 下降，先按 version lag 分桶看 reward，而不是只看平均值。若 slime 的同步模式已接近硬件上限，迁移 AReaL 未必有收益；若长尾和队列等待占大头，解耦才可能值得额外复杂度。

## 32.5 选择依据与追问

| 场景 | 更自然的起点 |
|---|---|
| 想先验证 reward、mask、advantage | 简单同步 trainer，必要时 TRL/verl |
| rollout 长尾明显、trainer 与 generation 速度不平衡 | AReaL/其他 actor--learner async |
| 团队已有 Megatron + SGLang，需 MoE/长上下文/agent 定制 | slime |

**验收：** 你能解释三份策略各自的作用，画出 AReaL 的 freshness 控制点和 slime 的 Data Buffer 边界，并用 profile 说明瓶颈属于生成长尾、权重同步还是 trainer。
