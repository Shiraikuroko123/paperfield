P20-P35 讨论显存、KV cache、精度、长尾、并行、异步和框架。系统问题最容易被框架名掩盖，先建立四本与实现无关的账。

## 1. 张量账

记录每个核心张量的 shape、dtype、device、是否需要梯度、生命周期和 owner。对 RL 样本至少包含 prompt/response ids、mask、old/current/reference log-prob、reward、advantage 与 policy version。

## 2. 字节账

分别计算：

- 参数、梯度、优化器状态；
- 激活与重计算；
- rollout 模型和 reference 模型副本/分片；
- KV cache；
- 通信 buffer、allocator 碎片和峰值临时张量。

框架报告的 allocated、reserved 和系统 `nvidia-smi` 含义不同，必须注明口径。

## 3. 时间账

一次 RL step 拆成：

```text
排队 → 权重同步 → prefill → decode → reward/验证 → 传输
    → log-prob/value → loss → backward → optimizer → checkpoint
```

每段记录均值和 P50/P95/P99，标注可重叠与不可重叠区间。GPU utilization 高不保证有效 token/s 高。

## 4. 版本账

每条样本保存：生成 policy version、训练消费 version、reference version、模型/Tokenizer hash 和时间戳。Staleness 不能只用“旧了几步”描述，还应测 sampled-token log-ratio、KL 或任务质量漂移。

## 框架选型顺序

1. 先写模型规模、序列长度、硬件、同步/异步和研究改动需求；
2. 再判断需要 Trainer 抽象、推理引擎、Megatron 后端还是可编排队列；
3. 用一个 golden batch 对齐 loss、mask、log-prob 和更新；
4. 最后比较吞吐、可观测性、可修改性和运维成本。

## 模块验收

- [ ] 为一个 7B 训练/rollout 拓扑画出四本账。
- [ ] 用 profiler 证明瓶颈，而不是凭利用率猜测。
- [ ] 在换框架前完成 golden-batch 数值对齐。
