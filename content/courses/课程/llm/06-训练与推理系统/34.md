## 34.0 先看一条样本如何旅行

一条样本从 prompt 到参数更新，至少经过：

```text
dataset -> rollout -> verifier/reward -> Data Buffer
        -> trainer 重算 log-prob -> advantage/filter
        -> Megatron forward/backward -> optimizer
        -> weight sync 回 rollout
```

任何一步丢掉 `policy_version`、`response_length` 或 `loss_mask`，最后都可能出现“loss 能跑，梯度却不是想要的目标”。

## 34.1 Data Buffer 应保存什么

建议一条记录至少包含：

```text
tokens, prompt_length, response_length, loss_mask
reward/raw_reward, truncated, finish_reason
sample_index, group_id, policy_version
rollout_log_probs (若可得), sampling config, verifier version
tool/environment state (agent 场景)
```

`rollout_log_probs` 可以在极严格的 on-policy 重算条件下省略，但这只是工程选择，不是数学上把 PPO 分母删掉。只要 rollout 与 trainer 的 kernel、精度、temperature/top-$p$ 支持集不同，最好保存实际 behavior log-prob。

## 34.2 从 ratio 到 token loss

对样本 $i$ 的第 $t$ 个 response token，旧概率和新概率分别为 $p_{old,i,t}$、$p_{new,i,t}$。先取 log 再相减，避免直接乘很小的概率：

$$
r_{i,t}=\exp\left(\log p_{new,i,t}-\log p_{old,i,t}\right).
$$

若 advantage 是整条 response 共用的 $A_i$，PPO surrogate 为

$$
L_{PPO}=-
\frac{\sum_{i,t}m_{i,t}
\min\left(r_{i,t}A_i,
\operatorname{clip}(r_{i,t},1-\epsilon,1+\epsilon)A_i\right)}
{\sum_{i,t}m_{i,t}}.
$$

`mask` 把 prompt、padding 和无效尾部排除；分母决定长 response 是否拥有更大总权重。GRPO 原始 recipe 常先对每条 response 做 token mean，再在 group 内求均值；Dr.GRPO、DAPO 等可能改为全 token 或长度不偏的归一化。不要只看函数名，必须查当前 commit 的 reducer。

截至本课程写作时，slime 的某些版本默认 per-sample reduction，显式 `--calculate-per-token-loss` 才切换到全 token mean，并允许 custom reducer。这个事实是版本限定，不应写成所有未来版本都如此。

## 34.3 Megatron 负责什么

Megatron 负责高效的 forward/backward、DP/TP/PP/EP collective、梯度裁剪和 optimizer step；它不会自动知道 reward、group advantage 或哪几个 token 应该 mask。上游 Data Buffer 必须把这些张量按 micro-batch、sequence packing 和并行布局正确搬到 trainer。

可以把一次 trainer step 写成：

```python
batch = buffer.pop(global_batch)
new_logp = megatron_teacher_forced_logp(batch.tokens)
if batch.rollout_log_probs is not None:
    old_logp = batch.rollout_log_probs.detach()  # exact behavior log-prob, if recorded
else:
    assert batch.on_policy_recompute_contract
    with torch.no_grad():
        old_logp = recompute_behavior_logp(batch, sampling_config=batch.sampling_config)
    old_logp = old_logp.detach()
log_ratio = new_logp - old_logp
ratio = log_ratio.exp()
surrogate = torch.minimum(ratio * batch.adv,
                          ratio.clamp(1-eps, 1+eps) * batch.adv)
loss_num = -(surrogate * batch.loss_mask).sum()
loss_den = batch.loss_mask.sum()
# helper must use the same global denominator and reducer_scale as Project 26
loss = global_token_mean(loss_num, loss_den,
                         reducer_scale=ddp_or_fsdp_reducer_scale)
loss.backward()
optimizer.step()
publish_new_version()
```

这是概念伪代码；真实实现还要处理 packed sequence 的 position、gradient accumulation、mixed precision、zero-variance group 和 checkpoint resume。若 `rollout_log_probs` 缺失，只有在冻结快照、sampler support、tokenizer、dtype 和重算 kernel 全部满足契约时才能走重算分支；否则应拒绝样本或明确使用近似 estimator。`global_token_mean` 不能只做本地 `.mean()`，它必须像 Project 26 一样显式处理全局分母及 DDP/FSDP 的梯度平均/求和约定。

## 34.4 最小 golden-batch 实验

手工制作两条 prompt、三条 response，固定 old log-prob、advantage 和 mask。用 NumPy 写一个 20 行参考 loss，再用 slime/Megatron 跑同一批，比较：

```text
loss numerator, denominator, final loss
per-token ratio, masked token count
每层 gradient norm, optimizer update
```

先在单卡对齐，再打开 TP/DP/EP。若单卡对齐而多卡不对齐，优先查 global reduction；若框架对齐而 rollout reward 不对齐，查 behavior log-prob、sampling config 和权重版本。

## 34.5 追问

- 为什么只保存 sequence log-prob 会失去 PPO 的什么能力？答：无法定位某个 token 的 ratio 越界、clip 位置和长尾错误。
- 为什么 `old_logp` 为空不代表 on-policy？答：只有在冻结快照、sampling support 和重算 kernel 完全一致时，trainer 才能精确重建它。
- 为什么换一个 reducer 会改变 reward 学习速度？答：长度归一化改变了每条轨迹及每个 token 的梯度权重，即使公式表面仍叫 GRPO。

**验收：** 你能从 Data Buffer 字段一路追到 Megatron 的 loss 分子/分母，并用 golden batch 定位一次 loss mismatch。
