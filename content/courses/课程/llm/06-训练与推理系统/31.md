## 31.0 先看一个复现失败

同一 checkpoint、同一 prompt、同一 seed，单独生成得到答案 A，放进 32 条请求的 batch 后得到答案 B。差异可能只在最后几位浮点数，却在 top-$p$ 边界改变了 token。这个项目要区分“随机数种子固定”与“计算路径确定”。

## 31.1 确定性模式能保证什么

一个合理起点是：

```python
import random, numpy as np, torch

seed = 1234
random.seed(seed)
np.random.seed(seed)
torch.manual_seed(seed)
torch.cuda.manual_seed_all(seed)
torch.use_deterministic_algorithms(True)
torch.backends.cudnn.benchmark = False
torch.backends.cuda.matmul.allow_tf32 = False
```

还需固定 DataLoader worker/rank 的 RNG、数据顺序、tokenizer、CUDA/CUBLAS 环境变量、NCCL 拓扑，以及 FlashAttention、MoE dispatcher、量化 kernel 的 deterministic 路径。某些算子没有确定性实现时，PyTorch 可能报错或显著降速；“打开一个开关”不是完整复现方案。

## 31.2 batch invariance 是什么

理想的 batch invariance 要求一个请求单独运行和与另一个请求混批时，得到相同的 logits（或在定义的容忍范围内相同）：

$$
f(x;\{x\})\approx f(x;\{x,x'\}).
$$

违反原因包括 matmul tile/split-K 选择、FlashDecoding 的 split-KV、padding/position mask、动态量化 scale、MoE capacity/tie、浮点归约顺序和 scheduler 改变 kernel shape。它和“固定 seed”不同：seed 只固定随机数流，不固定每一步的并行归约顺序。

## 31.3 atomic add 为什么不等于确定

`atomicAdd` 防止多个线程同时写同一地址造成数据竞争，但没有规定线程到达的顺序。浮点加法不满足结合律：

$$
(a+b)+c\ne a+(b+c).
$$

例如 $a=10^8$、$b=-10^8$、$c=1$，两种顺序在有限精度下可能得到 1 或 0。atomic add 只保证“每次写入完整”，不保证最终和唯一；它甚至可能正是 batch-dependent nondeterminism 的来源。

要获得更强确定性，需要固定 reduction tree/排序、使用 deterministic segmented reduction、提高累加精度，或把差异阈值写进验收标准。

## 31.4 最小对齐实验

对一个小模型操纵四个因素：单请求/批量、确定性 kernel 开/关、BF16/FP32 累加、同 seed/不同 seed。完整 factorial 设计有 $2^4=16$ 个组合；资源有限时可选一个正交子集，但要在报告中写清楚抽了哪些组合：

```text
single request / batch of 8
deterministic kernels on / off
BF16 / FP32 accumulation
same seed / different seed
```

记录最后一层 logits 最大绝对差、选中 token 的 log-prob 差、top-k overlap、router top-k 一致率。伪代码：

```python
model.eval()
with torch.no_grad():
    # 对齐 padding、position ids 和 attention mask，比较同一有效位置。
    logits_a = model(single_input_ids, attention_mask=single_mask).logits[0, -1]
    logits_b = model(batched_input_ids, attention_mask=batched_mask).logits[0, -1]
max_abs = (logits_a - logits_b).abs().max().item()
```

不同长度时不能直接拿最后一个 padded 位置比较；应取同一个 response/prompt 的有效 token 位置，并固定 tokenizer、padding side 和 position ids。

如果 logits 差异很小但 token 不同，检查该 token 是否位于 top-$p$ 截断边界；如果差异只在 MoE，记录每层 expert assignment。

## 31.5 项目验收与发散

你应能解释 atomic add 的“无数据竞争”与“可复现”区别，给出一个 batch-invariance 测试，并明确哪些差异是数值容忍范围、哪些差异会改变 RL 的 old log-prob。进一步追问：为了 exact replay，是否应该关闭所有 fused kernel？通常不应盲目关闭；应先找出真正产生分布漂移的 kernel，再在速度和可复现性之间设定可测的契约。
