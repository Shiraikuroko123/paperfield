## 25.0 先看一个现象

假设 `nvidia-smi` 显示 GPU 利用率 92%，但用户看到首 token 要等 2 秒，生成 100 个 token 又要等 10 秒。另一台机器 GPU 利用率只有 65%，却能更快返回。哪个更好？单独看 92% 没有答案，因为它没有告诉我们 GPU 在做 prefill、decode、通信还是等待内存。

本项目的目标是把“利用率”拆成可解释的数字，并区分 serving 的 KV cache 与训练 activation。

## 25.1 用一个小例子理解 KV cache

考虑一个 32 层模型，8 条请求，每条已有 4,096 个 token；每层有 8 个 KV head，每个 head 维度 128，使用 BF16（每个元素 2 字节）。每个 token 每层要保存 K 和 V 两份，所以粗略显存是

$$
M_{KV}=2\times32\times8\times4096\times8\times128\times2
\approx4.0\ \text{GiB}.
$$

逐项看这个乘法：第一个 2 是 K/V 两份，32 是层数，8 是并发请求数，4,096 是每条上下文长度，第二个 8 是 KV head 数，128 是 head dimension，最后一个 2 是 BF16 的字节数。把 GQA 的 KV head 从 8 减到 2，其他不变，KV 显存就约降到 1 GiB。

如果分页 block 一次容纳 16 个 token，一条长度 17 的请求仍要分配 32 个 token 的空间。分配浪费率是

$$
1-\frac{17}{16\lceil17/16\rceil}=1-\frac{17}{32}=46.875\%.
$$

所以“分配了多少”与“真正存了多少有效 token”必须分开记录。

## 25.2 prefill、decode 和三种吞吐

prefill 一次处理整个 prompt，通常矩阵乘法大、容易吃满 Tensor Core；decode 每轮只追加一个 token，却要读取历史 KV，常常更受 HBM 带宽限制。连续 batching 能在 decode 循环里动态加入/移除请求，但不会自动消除训练端等待完整 update 的 barrier。

要把三个容易混淆的吞吐分开：

$$
\text{engine\_tps}
=\frac{\text{窗口内实际生成的 response token 总数}}
 {\text{同一 wall-clock 窗口}} ,
\qquad
\text{accepted\_tps}
=\frac{\text{进入训练/评测的有效 token 总数}}
 {\text{同一 wall-clock 窗口}}.
$$

`engine_tps` 是引擎的 gross throughput；`accepted_tps` 是排除取消、padding 和被丢弃 stale 样本后的 useful goodput。二者都要报告，并另列 `dropped_tokens`、`cancelled_tokens` 与统计窗口；只报后者会把“生成了很多但全被丢掉”的系统看起来过于高效。还要同时报告 TTFT（首 token 延迟）、ITL（相邻 token 间隔）以及 p50/p95/p99，否则平均值会遮住长尾。

## 25.3 利用率指标表

| 层次 | 要问的问题 | 典型指标 |
|---|---|---|
| 硬件 | 算力还是带宽在限制？ | SM/Tensor Core、HBM GB/s、NVLink/PCIe/IB GB/s |
| 调度 | 请求是否在排队？ | active sequences、queue wait、scheduler step time |
| KV | cache 是否复用？ | allocated/used blocks、hit/miss、eviction、fragmentation |
| RL 端到端 | 哪个阶段拖慢 update？ | rollout tokens/s、verifier time、trainer time、weight-sync time |

KV 的两个简单比例是

$$
u_{KV}=\frac{\text{used KV bytes}}{\text{allocated KV bytes}},
\qquad
h_{prefix}=\frac{\text{被复用的 prefix token 数}}
{\text{本来可以复用的 prefix token 数}}.
$$

$u_{KV}$ 高只说明缓存被占满，不说明 prefix 命中；$h_{prefix}$ 高才说明重复 prefill 被省掉。

## 25.4 最小实验：让数字自己说话

固定 100 个 prompt，分别运行：静态 batch、continuous batching、continuous batching 加重复 prefix。每种设置至少记录一行 JSON：

```json
{"wall_s": 12.4, "prompt_tok": 51200, "response_tok": 38400,
 "ttft_p95_ms": 910, "itl_p95_ms": 78, "active_max": 64,
 "kv_alloc_bytes": 8589934592, "kv_used_bytes": 7340032000,
 "prefix_hit_tok": 18000, "candidate_prefix_tok": 24000,
 "accepted_tok": 32000, "dropped_tok": 6400, "queue_wait_s": 1.2}
```

再用下面的计算检查分母：

```python
engine_tps = response_tok / wall_s
accepted_tps = accepted_tok / wall_s
kv_util = kv_used_bytes / max(kv_alloc_bytes, 1)
prefix_hit_rate = prefix_hit_tok / max(candidate_prefix_tok, 1)
```

这里 `candidate_prefix_tok` 是“按当前 cache 规则，本来具备复用资格的 prefix token 数”，不是全部 prompt token。示例的 prefix 命中率是 $18{,}000/24{,}000=75\%$；少记这个分母，代码会直接报错，即使补成 prompt token 也会得到没有业务含义的比例。

把 `max_num_seqs` 从 8、16、32、64 逐步增加，画出 `engine_tps`、`accepted_tps` 和 `ttft_p95`。如果引擎吞吐继续增加但 accepted goodput 不增、p95 突然爆炸，系统已经进入排队或 KV eviction 区域；这不是“利用率越高越好”。

## 25.5 训练里的 KV 误区

标准 teacher-forcing forward/backward 通常保存 activation、checkpoint 和梯度，不保留 serving 式逐 token KV。训练应该测有效 token/s、padding ratio、FlashAttention 时间、activation recompute 比例、通信占比和峰值 HBM。只有 rollout 或 log-prob 重算阶段真的复用 prefix KV 时，才另外测 cache hit、失效原因和重算 token 数。

把 activation 叫作 KV cache 会造成两个错误：第一，误以为 backward 可以直接使用推理缓存；第二，误把 serving cache 命中率当成训练 MFU。两种内存的生命周期和读写模式不同。

## 25.6 常见失败与追问

- 只看 `nvidia-smi`：补上引擎 metrics、NCCL trace 和 profiler 时间戳。
- 把 block 分配量算进有效吞吐：改用完成 response token 数。
- prefix cache 命中但 log-prob 变了：检查 tokenizer、位置编码、权重 version、dtype 和 KV 量化误差。
- RL 中连续 batching 混了不同 version：每个 group 必须记录快照版本，或明确做 off-policy correction。

**验收：** 你能手算上面的 4 GiB，解释 SM 低而 HBM 高的含义，并从一份日志指出瓶颈在 queue、KV、通信还是 trainer。
