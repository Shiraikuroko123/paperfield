# Research Atlas：Paperfield 伴生研究知识平台与前沿雷达设计文档

> 状态：Draft v1.2
>
> 日期：2026-08-11
>
> 适用仓库：`paper-scout` / Paperfield，以及待新建的 Research Atlas companion
>
> 目标读者：产品、内容、数据、后端、前端与测试 agent

## 1. 执行摘要

Paperfield 当前已经具备论文聚合、筛选、合法公开 PDF 解析、全文精读、公式渲染、翻译、论文问答和 GitHub 项目导读。下一阶段不应继续在主工作台中堆叠孤立的“单篇摘要”，而应新建一个可以从 Paperfield 跳转的 Research Atlas companion。两者形成两个相互连接的研究系统：

1. **阅读驱动的研究知识平台**：用户在 Paperfield 中明确阅读或加入深度分析的论文，才进入高成本全文分析；输出研究问题、概念、理论、方法、数学、主张、证据和代码映射。
2. **广覆盖的前沿雷达**：低成本扫描每日新增论文、术语、GitHub 产物和相关新闻，把它们放回已有知识谱系，说明“什么发生了变化、证据有多强、它挑战了什么旧认识”。

核心产品判断：

- 论文是证据载体，不是知识组织的最小单位。
- 四万篇论文不应全部生成同等深度的长讲解。
- 用户实际阅读的论文进入高成本多阶段分析，其他论文只建立目录和前沿上下文。
- 稳定知识与每日热点必须分层存储、分开标注、相互链接。
- “方法好不好”必须拆成多个可审计维度，不能用一个星级或模型印象代替。
- 所有定量结论、公式解释和趋势判断必须能回到原论文页码、章节、图表或官方产物。
- Research Atlas 中的论文和 GitHub 项目必须能跳回 Paperfield 的精读工作台。

第一版成功标准不是“生成了多少摘要”，而是用户能从前沿研究线程发现新问题、新名词、主要论文、新闻和代码，跳回 Paperfield 进行精读；读过的论文又沉淀为可追溯的深度档案，并反过来补强 Research Atlas 的知识谱系。

### 1.1 已确定的部署边界

Research Atlas 是一个独立网页，可以独立部署、更新和浏览。它不嵌入 Paperfield 的单页应用，也不直接读取 Paperfield 的 SQLite 文件。

```text
Paperfield                         Research Atlas                         Flowloom
论文发现、PDF、个人阅读      <->    深度档案、知识谱系、前沿雷达     <->    图形重绘、编辑与导出
         |                               |                                  |
         +--------- canonical paper ref + versioned message bridge --------+
```

Paperfield 只新增少量显式入口：

- `查看系统讲解`：打开 Research Atlas 对应论文档案。
- `查看研究谱系`：打开论文所属问题、方法或前沿线程。
- `加入深度分析`：把当前论文和用户选定的分析重点交给 Atlas 的持久任务队列。
- 保留现有 `送到 Flowloom`：传输 PDF 页或选定图像。

Research Atlas 中的论文和项目分别提供 `在 Paperfield 精读` 与 `在 Paperfield 查看源码`。页面导航使用稳定 URL；分析任务由 Atlas API 持久化，消息桥只负责窗口握手、当前论文或页码上下文和任务回执。图片与 SVG 可以在限额内通过消息桥传输；私有 PDF 或全文只能通过用户确认的一次性上传通道传输。

Paperfield 现有的外接模型问答和单篇中文讲解继续作为阅读台内的快速解释能力，不必为了 Atlas 而删除。它们回答当前段落或临时问题；Atlas 负责需要跨论文检索、分阶段核查、数学重构、实验审计和长期维护的系统讲解。现有讲解默认仍是个人数据，不能自动成为 Atlas 的公共知识。

## 2. 当前基线

以下数据来自 2026-08-11 对本地仓库与只读数据库的检查：

| 项目 | 当前状态 |
|---|---:|
| 论文元数据 | 41,647 篇 |
| GitHub 项目 | 864 个 |
| 论文与项目关联 | 64 条 |
| 已解析全文 | 158 篇 |
| 已生成讲解 | 38 篇 |
| 论文问答消息 | 4 条 |
| 主要来源 | DBLP archive、Crossref、CVF、arXiv、PMLR、OpenAlex |

现有技术与产品能力：

- Python `SimpleHTTPRequestHandler` 服务端，SQLite 本地优先存储。
- 原生 HTML、CSS、JavaScript 客户端。
- 关键词驱动的两级主题分类与五维推荐权重。
- 单篇论文讲解已经包含背景、问题、方法、流程、公式、实验、结论、局限、前置知识、术语和页码证据。
- PDF.js、KaTeX、全文分块阅读笔记和基于原文的问答已经可用。
- `user_state.explanation_json` 目前同时承担个人阅读状态与讲解存储。

当前缺口：

- 没有跨论文共享的概念、方法和研究问题实体。
- 没有论文之间的继承、比较、反驳、复现和使用关系。
- 没有稳定知识与时效性趋势的版本边界。
- 没有系统性的批判评价模型与审核流程。
- 没有面向四万篇历史论文的分层处理策略。
- 没有趋势快照、变化原因和反证记录。
- 公共知识内容与个人笔记混在同一存储边界内。
- 当前讲解把全文页块高度压缩后再一次性合成，缺少多轮方法核查、公式重构、实验审计和跨论文检索，因此容易得到结构完整但内容笼统的结果。
- 当前论文讲解与项目源码导读相互分离，没有自动把论文模块映射到仓库入口、配置和实现文件。
- 没有“用户开始阅读 -> 后台深度分析 -> Atlas 档案完成”的任务闭环。
- 没有新术语的首次出现、别名、采用速度和“旧概念重新命名”识别。
- 没有论文、项目、官方发布与独立新闻之间的关联对象。

## 3. 产品目标与非目标

### 3.1 产品目标

1. 系统解释 LLM 与具身智能领域的基础概念、理论、方法和数学。
2. 只对用户明确阅读的论文执行高成本深度分析，让讲解从“复述摘要”升级为“主张、机制、推导、证据、边界、代码和评价”。
3. 用方法谱系连接历史论文，支持横向比较和纵向演化阅读。
4. 每日识别少量值得注意的新变化、新术语、代表论文、代码发布和新闻，而不是制造无限信息流。
5. 允许用户从基础知识一路追到当前前沿，也能从新论文反向补齐前置知识。
6. 所有公开结论都有来源、时间和生成版本，可被纠错与重算。
7. 在 Atlas 与 Paperfield 之间提供论文、页码和 GitHub 项目的双向深链接。

### 3.2 非目标

- 第一阶段不覆盖大模型与具身智能之外的全部科学领域。
- 不自动宣称某篇论文“正确”“SOTA”或“已经取代某路线”。
- 不对全部 41,647 篇论文生成同样昂贵的全文级讲解。
- 不把“打开过论文”直接等同于授权消耗模型额度；自动触发必须由用户设置，默认使用明确的“加入深度分析”动作。
- 不把 X、公众号、新闻稿或第三方笔记当作最终证据。
- 不未经许可复制第三方课程或论文笔记正文。
- 不在 MVP 阶段引入社交动态、公开评论区或复杂贡献者治理。
- 不为了展示关系而优先建设装饰性的 3D 知识图谱。

## 4. 核心用户任务

### 4.1 系统学习

用户希望回答：

- 这个领域有哪些真正基础的问题？
- 一个方法依赖哪些数学和理论？
- 代表论文之间是什么关系？
- 应该先读什么，后读什么？

产品输出：知识地图、概念页、方法页、问题页和学习路径。

### 4.2 精读一篇论文

用户希望回答：

- 作者到底提出了什么？
- 方法如何从输入走到输出？
- 目标函数从哪里来，各项起什么作用？
- 实验是否支持论文主张？
- 方法在哪些条件下有效，哪些条件下会失败？

产品输出：论文档案、数学推导、证据链、批判评价和相关论文。

默认交互闭环：

```text
Paperfield 打开论文
  -> 用户点击“加入深度分析”或把状态标为“在读”
  -> Research Atlas 持久化分析任务并返回 task ID
  -> 方法、数学、实验、代码和相关工作分阶段完成
  -> Paperfield 显示完成状态
  -> 用户在 Atlas 查看档案，随时跳回 Paperfield 对应 PDF 页
```

触发方式：

- 默认：显式点击 `加入深度分析`，避免误耗额度。
- 可选设置：论文状态从 `未读` 变为 `在读` 时自动加入队列。
- 已有相同论文版本的分析直接复用；新版本只重算受影响部分。
- 用户可以选择分析重点：数学、实验审计、代码映射或完整分析。
- 关闭 Atlas 或 Paperfield 页面不终止任务；暂停、取消和重试都操作同一个持久 task ID。

### 4.3 判断前沿变化

用户希望回答：

- 最近真正新增了什么能力、方法或证据？
- 最近出现了哪些新名词，它们是新概念还是旧概念换名？
- 这是一个新名字、旧方法组合，还是实质突破？
- 有多少独立团队在推进？
- 新结果是否改变已有结论？
- 代表论文、GitHub 产物和相关新闻分别有哪些？

产品输出：每日信号、新术语页、代表论文集、项目发布、新闻脉络、每周研究线程、月度领域地图和带版本的趋势页。所有论文和 GitHub 项目都能跳回 Paperfield。

### 4.4 从个人阅读回到前沿

前沿雷达同时提供两个视角：

- `全局前沿`：覆盖 LLM 与具身智能中经过筛选的近期变化，不依赖个人阅读历史。
- `与我的阅读相关`：只根据用户主动加入深度分析、主动关注的论文、方法和研究线程排序。

一篇论文完成任意分析阶段后，Atlas 都应立即给出与当前论文有关的前沿上下文：它属于哪些研究线程，出现了哪些新术语，哪些论文分别承担定义、奠基、代表、benchmark、复现或反证和最新进展角色，有哪些代码、模型、数据与可靠新闻。用户可以沿关系在 Atlas 中浏览，也可以随时回到 Paperfield 阅读论文或源码。

普通页面点击、停留时间和滚动行为不自动变成兴趣信号。个人关注范围与分析记录默认私有，不因补强公共知识谱系而公开用户读过什么。

## 5. 总体产品模型

```text
                         低成本广覆盖
论文、评审、代码、模型、数据集、新闻、项目页
                         |
                         v
              去重、术语检测、线程聚类
                         |
                         v
             前沿雷达与待读候选队列
                         |
        用户在 Paperfield 选择一篇论文阅读
                         |
                         v
                    高成本深分析
       全文 / supplementary / 图表 / 代码 / 相关工作
                         |
                         v
       深度论文档案 -> 方法谱系 -> 稳定研究知识层
```

Research Atlas 由六类内容组成：

1. **知识节点**：稳定、可维护的概念、理论、方法、问题和基准说明。
2. **论文档案**：一篇论文的结构化解释与证据评价。
3. **研究线程**：若干论文围绕同一问题形成的方法演化和争议。
4. **前沿信号**：带日期、证据状态和反证的近期变化。
5. **新术语**：记录术语定义、首次出现、别名、代表论文、使用变化和命名争议。
6. **新闻与发布**：把官方发布、独立报道和社区讨论连接回原论文与项目，但不混入学术证据评级。

三个系统的所有权边界：

| 内容 | 所有者 |
|---|---|
| 本地论文库元数据、PDF、个人收藏、笔记、阅读状态 | Paperfield |
| 跨来源 canonical 论文索引、版本和外部 ID 别名 | Research Atlas；Paperfield ID 只作为本地别名 |
| 用户触发的分析任务状态 | Atlas，Paperfield 只缓存显示状态 |
| 公共论文档案、知识节点、关系和趋势 | Research Atlas |
| GitHub 源码克隆与逐文件阅读 | Paperfield |
| 项目与研究线程的公共关系 | Research Atlas |
| 图像裁剪、重绘工程和 SVG | Flowloom |
| canonical paper ref 与跨站消息 Schema | 三者共同遵循的版本化协议 |

## 6. 知识分类体系

### 6.1 不使用单一文件夹分类

一篇论文必须允许同时挂接多个维度：

| 维度 | 示例 |
|---|---|
| 领域 | LLM、具身智能、跨领域 |
| 研究问题 | 长时序规划、动作泛化、幻觉、长上下文 |
| 方法族 | 自回归、扩散、flow matching、预测表征、强化学习 |
| 理论基础 | 概率建模、优化、信息论、控制、MDP、最优传输 |
| 模态 | 文本、图像、视频、深度、触觉、本体状态、动作 |
| 任务 | 推理、检索、操作、导航、locomotion、规划 |
| 本体 | 单臂、双臂、移动操作、人形、四足、软件 agent |
| 数据 | 互联网数据、示范轨迹、合成数据、仿真、真实数据 |
| 评测 | 数据集、benchmark、真实机器人、仿真、人工评测 |
| 成熟度 | 假设、早期信号、重复结果、独立验证、稳定基础 |

主题、方法和任务不得混成同一级标签。例如，VLA 是模型接口与研究范式，flow matching 是生成方法，LIBERO 是评测环境，长时序泛化是研究问题。

### 6.2 LLM 初始知识树

1. 数学与学习基础
2. Tokenization、embedding 与表示
3. Attention、Transformer 与序列建模
4. 架构、MoE 与 scaling
5. 数据、预训练与持续训练
6. SFT、偏好优化与强化学习后训练
7. 推理、搜索、验证器与测试时计算
8. 检索、记忆、工具使用与 agent
9. 多模态理解与生成
10. 长上下文与上下文管理
11. 评测、事实性、可靠性、安全与可解释性
12. 训练和推理效率

### 6.3 具身智能初始知识树

1. 坐标、运动学、动力学、状态估计与控制
2. 视觉、3D、触觉和多模态表征
3. 模仿学习、强化学习与 offline RL
4. 行为克隆、action chunking 与生成式策略
5. VLM、VLA 与机器人基础模型
6. 世界模型、动作条件预测与 JEPA 类预测表征
7. 规划、记忆、层次策略与 embodied agent
8. 操作、导航、locomotion 与全身控制
9. 数据采集、数据混合、仿真、合成数据与 Sim2Real
10. 跨任务、跨场景和跨本体泛化
11. 评测、复现、失败分析、安全与部署边界

这两棵树必须通过共享理论和方法交叉连接。例如，flow matching 同时连接生成建模与动作策略；JEPA 同时连接自监督表示、视频预测和世界模型；强化学习同时连接 LLM 后训练与机器人策略优化。

## 7. 核心内容对象

### 7.1 概念页

用于解释一个术语或基础概念：

- 精确定义和常见误用。
- 最小数学表达。
- 直觉解释。
- 与相邻概念的区别。
- 它解决什么问题、不解决什么问题。
- 首要来源与推荐阅读。
- 当前仍存在的争议。

### 7.2 方法页

方法页是平台最重要的稳定内容：

- 方法试图解决的研究问题。
- 输入、表示、模块、训练目标和推理输出。
- 理论依据、必要假设和数学推导。
- 与前代方法相比究竟改变了什么。
- 代表论文、反例论文和独立复现。
- 适用条件、计算和数据要求。
- 典型失败模式。
- 仍未解决的开放问题。
- 方法谱系和竞争路线对比。

### 7.3 问题页

问题页围绕行业或研究痛点组织：

- 可检验的问题定义。
- 为什么困难。
- 已知失败条件。
- 主要方法族及其假设。
- 支持与冲突证据。
- 使用的 benchmark 是否真正测到了该问题。
- 当前最有信息量的未决问题。
- 最近哪些结果改变了判断。

### 7.4 论文档案

论文档案不是普通摘要，必须使用第 8 节定义的内容合同。

### 7.5 研究线程

研究线程描述一个问题随时间发生的变化：

```text
问题提出 -> 早期方法 -> 关键失败 -> 新假设 -> 新方法 -> 独立验证或反证
```

每个线程要说明论文之间属于 `extends`、`uses`、`compares`、`replicates`、`contradicts`、`qualifies` 或 `surveys` 中的哪一种关系。

### 7.6 学习路径

学习路径不是固定课程目录，而是由知识依赖生成的阅读序列：

- 入门路径：概念、最小数学、经典论文。
- 研究路径：代表方法、关键对比、失败与开放问题。
- 前沿路径：近期论文、证据争议和待验证假设。

每个节点都必须回答“为什么现在读它”和“读完应该能解释什么”。

## 8. 论文档案内容合同

每篇全文级档案至少包含以下部分。

### 8.1 身份与来源

- 标题、作者、机构、日期、venue、版本。
- DOI、arXiv、OpenReview、项目页、代码、模型、数据。
- 当前材料基础：摘要、全文、supplementary、评审或代码。
- 生成时间、模型、提示版本、全文哈希和审核状态。

### 8.2 一句话结论

使用“任务或问题 + 方法变化 + 证据范围”表达，不使用“首次”“领先”“革命性”等无法核验的词。

### 8.3 问题与假设

- 作者明确提出的问题。
- 方法成立依赖的关键假设。
- 论文实际测试的问题是否与标题宣称一致。

### 8.4 方法拆解

固定按以下顺序解释：

```text
输入 -> 表示 -> 核心模块 -> 训练目标 -> 优化过程 -> 推理过程 -> 输出
```

同时标出相较最近强基线真正新增、替换或删除的组件。

### 8.5 理论与数学推导

数学部分必须包含：

1. 符号表和变量维度。
2. 假设、目标和概率或优化对象。
3. 原文给出的关键公式。
4. 从目标到损失或算法更新的逐步推导。
5. 每一项对应的直觉和实现位置。
6. 极端情况、退化形式或与旧方法的等价关系。
7. 原文没有提供的推导必须标记为“平台重构推导”。

如果论文只是使用经验性设计而没有理论保证，应直接写明，不得为了完整而虚构理论。

### 8.6 实验证据

- 数据集、拆分、任务和样本规模。
- baseline 是否足够强，配置是否公平。
- 指标是否对应论文主张。
- 主结果、方差、置信区间和统计检验。
- 消融是否真的隔离关键变量。
- OOD、长时序、跨任务或跨本体结果。
- 失败案例、负结果和未报告条件。
- 算力、数据和硬件成本。

所有数值必须链接到页码、表格或图编号。

### 8.7 批判性评价

不要输出一个总星级。每个维度使用 `强 / 中 / 弱 / 无法判断`，并附置信度与证据：

| 维度 | 判断问题 |
|---|---|
| 问题价值 | 是否解决真实且重要的问题？ |
| 新颖性 | 是新机制、新组合、新规模，还是新命名？ |
| 理论合理性 | 假设和推导是否成立？ |
| 实验效度 | 实验是否真正测试核心主张？ |
| 基线公平性 | 是否遗漏强基线或使用不等预算？ |
| 统计可靠性 | 是否报告方差、重复试验和显著性？ |
| 泛化与鲁棒性 | 结论是否跨任务、数据和环境成立？ |
| 可复现性 | 代码、数据、配置和权重是否足够？ |
| 成本收益 | 收益是否值得额外数据、算力和复杂度？ |
| 适用边界 | 在什么条件下值得用，什么时候不值得？ |

最终评价固定输出：

- **总体判断**：有说服力 / 有条件成立 / 证据不足 / 当前证据不支持。
- **最强证据**：论文最有力的一项结果。
- **最弱环节**：推理链最容易断裂的地方。
- **适用条件**：何种数据、任务和资源下值得使用。
- **改变判断所需证据**：需要怎样的独立实验或反例。

### 8.8 内容来源标签

每一项分析必须属于以下一种：

- `原文明确`：原文直接陈述，并附定位。
- `根据原文推导`：平台根据公式或实验进行推导，并展示过程。
- `跨论文综合`：来自多篇论文的综合判断，并列出来源。
- `编辑评价`：主观评价，必须给理由和置信度。
- `信息不足`：当前材料无法判断。

### 8.9 阅读驱动的深度分析

当前单次“生成中文讲解”不再作为目标形态。深度档案由若干独立任务组成，允许逐项完成、失败重试和局部重算。

#### 分析输入

- 论文元数据、当前版本和合法获得的全文。
- PDF 页码映射、章节结构、公式、图表标题与参考文献。
- supplementary、appendix、OpenReview 评审与 rebuttal。
- 官方项目页、关联 GitHub README、版本、release 和关键入口文件。
- 从历史语料检索到的前代工作、强 baseline、后续工作、复现和反证。
- 用户选择的分析重点与用户在 Paperfield 中选中的段落或页码。

#### 多阶段任务

| 阶段 | 输出 | 失败时的行为 |
|---|---|---|
| 结构解析 | 章节、图表、公式、引用和页码索引 | 保留 PDF，标记解析失败 |
| 主张抽取 | 作者主张、假设和贡献候选 | 不进入评价阶段 |
| 方法拆解 | 输入、表示、模块、目标、训练和推理 | 显示缺失环节 |
| 数学重构 | 符号表、原式、推导、直觉和退化形式 | 明确“原文未给出” |
| 实验审计 | 数据、基线、预算、指标、方差、消融和失败 | 不输出总体判断 |
| 代码映射 | 论文模块到仓库文件、类、配置和 checkpoint | 仅显示官方仓库状态 |
| 相关工作检索 | 奠基、直接前代、竞争、复现、反证和后续论文 | 显示检索覆盖范围 |
| 批判审阅 | 最强证据、最弱环节、适用条件和待验证项 | 保留前面已验证内容 |
| 引证核查 | 数字、公式、页码、图表和链接一致性 | 阻止发布相关主张 |

#### 输出不是一篇长作文

前端按完成状态逐步开放以下标签页：

- `速览`：只给问题、核心变化和阅读建议。
- `方法`：模块级拆解及与前代方法的差分。
- `数学`：可逐步展开的符号、公式和推导。
- `实验审计`：主张与实验是否一一对应。
- `代码映射`：论文概念到 GitHub 实现入口。
- `研究谱系`：主要论文、竞争路线和后续演化。
- `批判评价`：分维度判断和改变判断所需证据。

每一部分独立保存版本和来源。用户无需等待完整档案完成后才能开始阅读。

#### 成本与复用

- 相同 canonical paper ref、论文版本和全文哈希共享公共分析结果。
- 用户私人选文、笔记和问题不进入公共档案，除非用户明确发布。
- 只重算版本变化涉及的章节、主张和证据，不整篇重新生成。
- 代码仓库更新只使代码映射过期，不使论文数学分析过期。
- 高成本分析设置并发、日额度和取消按钮，任务可暂停和恢复。

### 8.10 论文与代码的联合讲解

论文档案发现官方或高置信度仓库后，建立以下映射：

```text
论文方法模块 -> 仓库目录/文件 -> 关键类或函数 -> 配置项 -> 权重/数据入口
```

代码映射必须区分：

- 作者官方仓库。
- 官方组织下的实现。
- 作者认可的移植版本。
- 独立第三方复现。
- 仅名称或关键词相似的候选项目。

Atlas 只展示公共映射和项目状态。点击 `在 Paperfield 查看源码` 后，使用项目完整名称跳转到 Paperfield 已有的 `?project={owner/repo}` 代码工作台。

## 9. 前沿雷达设计

### 9.1 前沿信号来源

核心来源限定在 LLM 与具身智能：

- arXiv、OpenReview、PMLR、CVF、DBLP、Crossref、OpenAlex。
- NeurIPS、ICML、ICLR、ACL、EMNLP、CVPR、ICCV、ECCV。
- RSS、CoRL、ICRA、IROS、RA-L、T-RO、IJRR。
- 官方项目页、代码、模型权重、数据集、benchmark 和技术报告。
- 评审意见、rebuttal、复现、负结果和勘误。
- 作者或实验室的官方发布、研究博客和发布说明。
- Nature、Science、Quanta、MIT Technology Review、IEEE Spectrum 等独立科技报道，以及可核验的中文科技报道。

官方博客可以证明“团队发布了什么”，不能单独证明方法有效；独立新闻可以证明“外部如何解读”，不能替代论文证据。社交媒体和未署名聚合内容只能触发候选信号。

### 9.2 信号类型

- 新研究问题。
- 新术语、新缩写或旧术语含义发生变化。
- 新方法或关键机制变化。
- 旧方法在新规模或新数据上的扩展。
- 新 benchmark 或评测协议。
- 独立复现、反证或负结果。
- 代码、权重或数据正式发布。
- 官方发布、独立新闻或重要争议出现。
- 原有趋势发生合并、分裂或降温。

### 9.3 增量分析流程

```text
每日新增
  -> 去重与版本合并
  -> 多轴分类和实体链接
  -> 新术语、别名和命名漂移检测
  -> 与已有方法、问题和论文比较
  -> 提取“新增主张”和证据
  -> 聚合为候选研究线程
  -> 计算趋势维度
  -> 自动校验
  -> 人工审核高影响条目
  -> 发布带日期的雷达
```

系统必须首先回答“它相对已有知识新增了什么”，再决定是否进入前沿雷达。仅仅换名称、换 backbone 或在相同设置小幅提分，不自动构成新趋势。

### 9.4 趋势维度

趋势维度分别展示，不合成一个模糊热度分：

| 维度 | 含义 |
|---|---|
| 相关性 | 与用户关注的问题距离 |
| 新颖性 | 是否改变问题、假设、机制或证据 |
| 速度 | 一定时间窗内的新增研究数量变化 |
| 独立性 | 是否来自不同团队、机构和数据 |
| 证据强度 | 摘要主张、全文实验、评审、复现的层级 |
| 产物完整度 | 代码、数据、权重和协议是否公开 |
| 争议度 | 支持与反对证据是否同时增加 |
| 成熟度 | 候选信号、形成趋势、得到验证或进入稳定知识 |

默认状态规则可配置：

- `候选信号`：一个可信来源提出可识别的新主张。
- `形成趋势`：在限定时间窗内出现多个独立团队的同类工作，或一个高影响工作同时提供强证据与开放产物。
- `得到验证`：出现独立复现、跨 benchmark 结果或公认评测下的一致证据。
- `存在争议`：高质量支持与反对证据并存。
- `进入基础层`：概念和证据已经稳定，应从热点流迁入知识页。
- `降温或未兑现`：后续没有重复证据，或关键主张被反证。

算法只建议状态，编辑可以覆盖，但覆盖必须记录理由。

### 9.5 前沿内容格式

每日雷达最多展示 5 到 10 个条目，每个条目固定包含：

- 发生了什么变化。
- 它连接到哪个既有问题或方法。
- 最关键的论文和产物。
- 新出现或含义发生变化的术语。
- 当前支持证据。
- 当前反证或未知项。
- 相关 GitHub、模型、数据集和新闻。
- 为什么值得关注。
- 截止日期和成熟度。

每周输出 2 到 4 个研究线程，回答“本周哪些认识真的发生了变化”。每月更新领域方法地图和开放问题，不按论文数量简单排行。

### 9.6 新术语与新名词

新术语页必须回答：

- 这个词最早在当前语料中的出现时间和来源。
- 作者如何定义它，不同论文是否使用相同含义。
- 它连接到哪个已有概念、方法或研究问题。
- 它是新机制、新应用、新组合、品牌命名，还是旧概念换名。
- 哪些论文真正使用该术语，哪些只是平台根据相似性关联。
- 独立团队采用数量与时间变化。
- 当前推荐使用的中文译名、英文原词、缩写和别名。
- 术语是否已经稳定，还是仍存在命名竞争。

术语状态使用：

- `首次观察`：只有一个来源，含义可能不稳定。
- `多源采用`：多个独立团队使用相同或接近的含义。
- `命名竞争`：多个词描述相近机制。
- `旧概念换名`：与已有方法高度重合，新增内容有限。
- `稳定术语`：已进入方法页或概念页，不再作为每日新词突出展示。

模型提出术语候选后，系统必须检查标题、摘要、正文定义句、引用链和时间；不能仅凭词频认定“新概念”。

### 9.7 代表论文选择

一个研究线程的“主要论文”按角色组织，不按引用数混排：

- `定义论文`：首次清楚定义问题、术语或方法。
- `奠基论文`：提供关键理论或前代机制。
- `代表论文`：给出当前最完整的实现与证据。
- `benchmark 论文`：定义主要数据集、任务或评测协议。
- `复现或反证`：验证、限制或否定核心主张。
- `最新进展`：在最近时间窗内提供实质新增内容。

每个角色可以为空，但不能用不匹配的论文补齐版面。论文卡必须有 `在 Paperfield 精读`，有页码证据时同时提供 `跳到证据页`。

### 9.8 新闻与发布

新闻对象必须连接到至少一篇论文、一个项目、一个研究机构或一个趋势线程，并记录：

```text
标题、来源、作者、发布日期、URL、来源类型、关联对象、关联理由、抓取时间
```

来源类型：

- `official_release`：作者、实验室、公司或项目官方发布。
- `independent_reporting`：独立科技或大众媒体报道。
- `analysis_commentary`：有署名的研究分析或评论。
- `discovery_only`：社交帖子和聚合内容，只用于发现，不默认公开。

新闻展示必须把“论文实际结论”和“新闻标题的表述”并排区分。官方新闻中的性能数字仍需回到论文或技术报告核验。没有相关新闻时直接显示“未找到可靠报道”，不自动生成新闻摘要填充空白。

### 9.9 GitHub、模型与数据产物

前沿线程显示：

- 官方代码、权重、数据与 benchmark。
- release 日期、最近提交、许可证和归档状态。
- 论文声明开源但尚未发布的缺口。
- 高质量独立复现及其与官方实现的差异。
- `在 Paperfield 查看源码` 深链接。

Stars、forks 和社交热度只作为采用线索，不作为科学证据或项目质量结论。

## 10. 四万篇历史论文的分层处理

### 10.1 分层原则

历史语料必须分层，不应一次性全文生成：

| 层级 | 目标范围 | 处理内容 |
|---|---:|---|
| L0 目录层 | 全部 41,647 篇 | 元数据、去重、主题、版本、引用和来源 |
| L1 结构层 | 约 20% 到 30% | 摘要级问题、方法族、任务、数据和关系候选 |
| L2 档案层 | 用户实际阅读论文 + 编辑选定锚点；首期 100，逐步扩展 | 全文讲解、数学、实验、代码、证据和评价 |
| L3 综合层 | 首期 20，逐步到 100 至 200 个主题 | 方法页、问题页、研究线程和学习路径 |

数量是资源规划基线，不是永久上限。覆盖优先级根据知识缺口和前沿相关性动态调整。

L2 的第一优先级始终是用户明确加入深度分析的论文。编辑锚点用于补齐方法谱系，不得挤占用户分析队列的额度。用户未阅读的普通论文即使位于热门领域，也不会自动进入全文级处理。

### 10.2 锚点论文选择

优先选择：

- 定义问题或方法的奠基论文。
- 被大量后续工作直接复用的 baseline。
- 建立数据集或 benchmark 的论文。
- 改变方法结构或训练目标的代表工作。
- 对主流结论给出反例、复现或负结果的论文。
- 近期与已有谱系发生实质连接的新论文。

不能只按引用数选择。引用数对新论文有时间偏差，也会放大热门领域和综述文章。

### 10.3 首期黄金集

建立 60 篇人工审核黄金集：LLM 30 篇、具身智能 30 篇。黄金集需覆盖：

- 基础理论、代表方法、benchmark、复现或反证。
- 含数学推导和不含理论推导的论文。
- 摘要可用但全文不可用的边界情况。
- 真实机器人、仿真、生成数据和纯模型评测。
- 支持与反对同一研究主张的论文对。

所有提示词、抽取器、关系识别和前端渲染先在黄金集验收，再批量运行。

## 11. 内容生产与校验流水线

### 11.1 状态机

```text
discovered
  -> metadata_ready
  -> fulltext_ready
  -> extracted
  -> linked
  -> auto_verified
  -> editor_reviewed
  -> published
  -> stale / superseded
```

任何失败都保留错误原因和可重试状态，不以空内容冒充成功。

### 11.2 多阶段生成

1. **解析**：识别章节、页码、公式、图表标题、参考文献和 supplementary。
2. **抽取**：分别抽取问题、假设、方法、公式、实验、结论和局限。
3. **实体链接**：链接到已有概念、方法、任务、数据集和 benchmark。
4. **主张证据化**：为主张建立支持、反对或限定证据。
5. **跨论文比较**：只在同任务、同数据和可比预算下比较。
6. **教学重写**：从依赖图生成前置知识和解释顺序。
7. **批判评价**：根据第 8.7 节逐维评价。
8. **自动校验**：检查页码、数值、公式和引用是否存在。
9. **人工审核**：审核方法页、趋势页和高影响论文。

### 11.3 模型允许与禁止的工作

模型可以：

- 去重、翻译、聚类和生成候选标签。
- 从全文提取结构化信息。
- 重构并解释原文公式。
- 提出关系候选与批判问题。

模型不能独立决定：

- 一篇论文是否真实领先。
- 一个结果是否被领域接受。
- 两个实验是否公平可比。
- 某个趋势是否已经成为共识。
- 缺失数据、公式或实验数字。

### 11.4 自动校验规则

- 数字型主张必须有页码和表格或图编号。
- 引用页码必须落在 PDF 页数范围内。
- 原文公式与平台重构推导必须分开。
- 评价用语必须有对应证据或标记为编辑判断。
- 论文版本变化后，旧分析自动标记 `stale`。
- 相同 DOI、arXiv ID、OpenReview ID 或标准化标题需版本合并。
- 摘要级分析不得展示为全文级结论。
- 无法获取全文时，数学、实验和局限字段显示“信息不足”。

## 12. 数据模型

### 12.1 设计原则

- Paperfield 保留现有 `papers`、`paper_assets`、`user_state`、GitHub 项目和聊天数据。
- 下述新表归 Research Atlas 自己的数据库所有，不加入 Paperfield 的 SQLite 文件。
- 两个应用只通过 canonical paper ref、公开 API、深链接或明确授权的消息桥交换数据。
- 公共知识内容不得继续只存入 Paperfield 的 `user_state.explanation_json`。
- 个人阅读状态与共享研究分析分离。
- 用户触发的分析默认私有；经过审核或用户明确发布后，才进入共享论文档案。
- 查询频繁的实体和关系正规化；长篇展示内容允许存 JSON。
- MVP 使用 SQLite 的节点表与边表即可，不需要先引入图数据库。

## 13. API 合同

以下是 Research Atlas 自己的 API，不直接追加到 Paperfield 的现有单文件服务：

```text
GET  /api/knowledge/nodes
GET  /api/knowledge/nodes/{slug}
GET  /api/knowledge/graph?root={id}&depth={n}
GET  /api/papers/resolve?ref={canonical_ref}
GET  /api/papers/{id}/dossier
POST /api/analysis-requests
GET  /api/analysis-requests/{id}
POST /api/analysis-requests/{id}/pause
POST /api/analysis-requests/{id}/resume
POST /api/analysis-requests/{id}/cancel
POST /api/analysis-requests/{id}/retry
GET  /api/papers/{id}/relations
GET  /api/projects/relations?repo={owner/repo}
GET  /api/trends?window=7d&domain=embodied&scope={global|my-reading}
GET  /api/trends/{slug}
GET  /api/terms?status=emerging
GET  /api/terms/{slug}
GET  /api/news?thread={id}
GET  /api/artifacts?paper={canonical_ref}
GET  /api/me/watchlists
PUT  /api/me/watchlists/{id}
GET  /api/learning-paths
GET  /api/learning-paths/{slug}
GET  /api/research-search?q={query}&types={types}
POST /api/editor/reviews/{content_type}/{id}
```

公共读取响应必须包含：

```json
{
  "content": {},
  "source_basis": "fulltext",
  "as_of_date": "2026-08-11",
  "status": "editor_reviewed",
  "provenance": {
    "paper_version": "...",
    "source_sha256": "...",
    "model": "...",
    "prompt_version": "..."
  }
}
```

批量分析、重算、审核和发布接口只允许管理员或编辑角色调用。

`POST /api/analysis-requests` 是创建高成本分析任务的唯一持久入口。Paperfield 发出的消息只负责把当前上下文交给 Atlas 前端；Atlas 必须在自己的服务端写入任务后才能返回 `atlas:analysis-accepted`。浏览器窗口关闭、刷新或跨站消息超时都不能让已接受任务丢失。`retry` 请求必须指定失败阶段，默认不重算已经核查通过的阶段。

Atlas API 路径中的论文 `{id}` 一律表示 `canonical_papers.id`，不接受 Paperfield 本地 ID。外部调用先使用 `GET /api/papers/resolve?ref=` 解析 canonical ref，避免两个系统的 ID 空间混用。

### 13.1 论文与项目深链接

跨站导航不依赖 CORS，也不传输全文：

```text
Paperfield -> Atlas 论文档案
{atlas_base}/paper?ref={canonical_ref}&paperfield_id={paperfield_id}

Paperfield -> Atlas 研究谱系
{atlas_base}/paper?ref={canonical_ref}#lineage

Paperfield -> Atlas GitHub 项目研究关联
{atlas_base}/project?repo={url_encoded_owner/repo}

Atlas -> Paperfield 论文精读
{paperfield_base}/?paper={paperfield_id}

Atlas -> Paperfield GitHub 源码导读
{paperfield_base}/?project={owner/repo}
```

Paperfield 当前已经支持 `?paper={id}` 和 `?project={owner/repo}`。后续增加以下定位：

```text
{paperfield_base}/?paper={paperfield_id}&reader=1&page={page_number}
{paperfield_base}/?paper_ref={url_encoded_canonical_ref}&action=resolve
```

如果 Atlas 已知 Paperfield 本地 ID，使用第一条 URL 直接定位 PDF 页；如果只有 canonical ref，使用第二条 URL，由 Paperfield 查找现有论文或显示导入确认。实现 `paper_ref` 路由前，Atlas 必须显示 `尚未导入 Paperfield`，不能猜测本地 ID，也不能把 canonical ID 填进 `?paper=`。

### 13.2 跨站消息协议

延续现有 `paperfield:pdf-page` v1，但新增通用信封：

```json
{
  "type": "paperfield:analysis-request",
  "version": 1,
  "messageId": "uuid",
  "bridgeToken": "one-time-token",
  "sourceOrigin": "http://127.0.0.1:8765",
  "paper": {
    "canonicalRef": "arxiv:2405.00001",
    "paperfieldId": "...",
    "title": "...",
    "version": "v2",
    "sourceSha256": "..."
  },
  "request": {
    "sections": ["method", "math", "experiments", "code", "lineage"],
    "visibility": "private"
  }
}
```

消息类型：

- `paperfield:analysis-request`：用户明确要求 Atlas 深度分析。
- `atlas:analysis-accepted`：返回任务 ID 和预计阶段。
- `atlas:analysis-status`：Paperfield 查询或接收进度。
- `paperfield:pdf-page`：保持现有 PDF 页面到 Flowloom 的兼容。
- `atlas:figure-to-flowloom`：Atlas 将有来源的图像或重绘请求送到 Flowloom。
- `flowloom:svg-export`：可选，将用户确认的 SVG 和来源元数据返回 Atlas。

`paperfield:analysis-request` 是创建任务的引导消息，不是内存任务本身。Atlas 收到后调用自己的 `POST /api/analysis-requests`；只有数据库事务提交成功，才发送包含 task ID 的 `atlas:analysis-accepted`。

协议必须具有：

- 精确目标 origin 白名单。
- URL hash 中的一次性 bridge token。
- `ready -> payload -> ack` 握手与 messageId 去重。
- MIME、尺寸、页码、文件大小和来源哈希校验。
- 用户对全文、图片和生成结果的明确共享确认。
- 禁止传输 API Key、本地文件路径和未授权私人笔记。

Paperfield 当前使用延迟重复发送而没有 ack；新协议实现后保留旧消息兼容，但新类型必须使用握手。

### 13.3 分析材料传输

Atlas 获得分析材料的优先级：

1. 根据 canonical ref 自行获取合法公开 PDF、supplementary 和官方仓库。
2. 比较 Atlas 下载文件与 Paperfield 提供的 `sourceSha256`，确认版本一致。
3. 只有材料不存在公开副本时，才向用户请求从 Paperfield 显式传输。

私有材料不能通过 URL query、localStorage 或长 `postMessage` 直接发送。推荐流程：

```text
用户在 Paperfield 确认共享当前论文用于私人分析
  -> Atlas 创建 analysis request 并返回一次性 upload token
  -> Paperfield 服务端向 Atlas 上传带页码文本或 PDF
  -> Atlas 校验 token、大小、MIME、canonical ref 与 SHA-256
  -> token 失效，材料只归该用户的 private analysis 使用
```

上传包只允许包含：

- 论文 canonical ref、Paperfield ID、标题、版本和来源 URL。
- 带页码标记的解析文本或用户确认的 PDF。
- 用户明确选中的页码或文本。
- 官方或高置信度 GitHub 项目引用。

默认不包含个人笔记、聊天记录、API Key、本地路径和其他论文文件。Atlas 使用自己的 OpenAI-compatible 模型配置；未来可以增加 Paperfield 服务端代理，但代理也不能把密钥返回浏览器或 Atlas。

## 14. 信息架构与页面设计

### 14.1 一级导航

Research Atlas 使用独立导航：

1. 前沿雷达
2. 研究线程
3. 新术语
4. 方法与问题
5. 论文与项目
6. 我的深度分析
7. 学习路径

Paperfield 原有一级导航保持不变，只在论文详情、PDF 阅读台和项目详情中加入上下文跳转。Atlas 不复制“今日视野”“顶会顶刊”、收藏和 PDF 阅读器。

### 14.2 前沿雷达页

首屏直接展示：

- 截止日期和覆盖来源。
- `全局前沿 / 与我的阅读相关` 分段切换；后者只使用显式关注信号。
- 本日或本周真正发生变化的研究线程。
- 每个线程的成熟度、证据和反证状态。
- “与上期相比发生了什么”。
- 本期新术语、代表论文、代码或权重发布和可靠新闻。

不使用营销落地页、新闻式大标题或单纯按热度排序。默认首页就是可操作的前沿雷达。每条信号必须能展开到论文、方法页和证据定位，并直接提供 `查看研究线程`、`在 Paperfield 精读` 或 `在 Paperfield 查看源码` 等真实可用的下一步动作。

### 14.3 研究线程与新术语页

研究线程页是前沿洞察的主要落点：

1. 线程名称、状态、首次观察和截止日期。
2. 它试图解决的真实研究痛点。
3. 新术语定义、别名及其与旧概念的差别。
4. 定义论文、奠基论文、代表论文、benchmark、复现或反证和最新进展。
5. 支持证据、反对证据和仍未知的条件。
6. 官方 GitHub、模型、数据集和 release 状态。
7. 官方发布、独立新闻与论文实际结论的对照。
8. 下一步最值得验证的假设。

论文、项目和新闻可以在 Atlas 内沿关系继续浏览。每篇论文和每个 GitHub 项目都提供 Paperfield 动作；新闻始终打开原始来源，不在 Atlas 中伪装成论文内容。

### 14.4 知识地图页

- 默认使用可扫描的树、矩阵和面包屑，不默认展示力导向关系图。
- 支持 LLM、具身智能和交叉领域切换。
- 显示前置知识、竞争方法和未解决问题。
- 关系图作为局部探索工具，限制深度和节点数。

### 14.5 方法页

页面顺序：

1. 方法定义和解决的问题。
2. 核心机制图或公式。
3. 数学推导。
4. 与相邻方法的对比表。
5. 代表论文时间线。
6. 支持、反证和限定证据。
7. 失败模式与开放问题。
8. 学习路径和原始资源。

### 14.6 论文档案页

采用稳定标签页或锚点导航：

- 总览
- 方法
- 数学
- 实验与证据
- 批判评价
- 关系与谱系
- 原文与产物

原文、平台推导和编辑评价必须使用清晰标签，不依赖颜色单独区分。

档案页的固定动作条：

- `在 Paperfield 精读`
- `跳到证据页`
- `在 Paperfield 查看源码`
- `送到 Flowloom`
- `查看原论文`

只在对应资源真实存在时显示动作。论文与 GitHub 项目在 Atlas 内可以沿关系连续跳转，但查看 PDF、个人笔记和逐文件源码时回到 Paperfield。

### 14.7 我的深度分析页

显示用户主动触发的任务，而不是全站生成队列：

- 等待、运行、部分完成、失败、已完成和已过期状态。
- 当前完成阶段和可立即阅读的部分。
- 本次分析重点、模型、额度和材料基础。
- 暂停、取消、局部重试和新版本重算。
- 从 Paperfield 打开的论文入口。

任务完成后仍保留 `private`。用户可以选择只把非私人、已核查部分贡献到公共 Atlas。

### 14.8 领域证据呈现

- 具身智能论文优先展示真实机器人、仿真、遥操作和生成数据的明确标签。
- 成功率必须同时展示任务、机器人、试验次数、环境和 baseline。
- LLM 论文优先展示评测协议、数据污染风险、推理预算和方差。
- 失败、限制和负结果不得埋在页面末尾。
- 公式、表格和证据定位在移动端允许独立横向滚动，不压缩到不可读。

## 15. 参考项目使用规则

### 15.1 `ai-systems-courses`

检查到的课程结构包含 LLM 与具身智能两条系统路线，覆盖基础数学、Transformer、RL、VLA、world model、评测和专题讲解。它适合用于：

- 初始知识树和前置依赖的参考。
- 教学内容的章节颗粒度参考。
- “问题、方法、证据、局限”讲解顺序参考。

检查时仓库根目录未发现明确的 `LICENSE` 或 `COPYING` 文件。公开仓库不等于允许复制。除非获得作者授权，不应导入、改写或公开发布其正文，只能把它作为结构参考并重新基于原论文创作。

部分课程文字含有强断言、时间敏感结论和宣传式判断。任何进入 Research Atlas 公共知识层的内容都必须重新核查原论文、官方项目页和评测设置。

### 15.2 `Paper-Notes`

该仓库覆盖大量顶会论文，并按会议和研究领域组织，适合用于：

- 补充候选论文清单。
- 参考五分钟笔记的信息颗粒度。
- 检查分类遗漏和相关论文关系候选。

其 README 声明内容采用 `CC BY-NC-SA 4.0`：

- 商业产品不得直接复用，除非另获许可。
- 非商业复用也必须署名并使用相同方式共享。
- 第三方解读只能作为发现线索，不能作为论文事实的最终证据。

Research Atlas 应根据合法获得的论文材料独立生成分析，不批量复制第三方笔记正文。Paperfield 只提供用户拥有或可合法访问的阅读上下文，不承担公共内容生产。

## 16. 科学质量与编辑治理

### 16.1 发布等级

- `自动抽取`：未经人工审核，只用于检索和候选关系。
- `自动讲解`：通过规则校验，可供阅读，但明确标注模型与材料基础。
- `编辑核查`：关键事实、公式和证据已核对。
- `专家审阅`：领域专家确认，可作为方法页或趋势页核心内容。

### 16.2 纠错机制

- 每个公开分析提供“报告事实错误”入口。
- 纠错必须定位到具体主张、公式或证据。
- 修订保留历史版本与修改理由。
- 作者反馈不得直接覆盖内容，应进入审核队列。

### 16.3 趋势治理

- 趋势页必须显示 `as_of_date`。
- 没有后续证据的候选趋势会自动进入复核队列。
- 新反证出现时，不能静默删除旧判断；应追加状态变化说明。
- “领域共识”只在有多来源证据时使用。

## 17. 衡量指标

### 17.1 覆盖

- L0 元数据去重覆盖率。
- 主题与方法实体链接覆盖率。
- 各知识分支的锚点论文覆盖率。
- 支持与反证论文的平衡程度。

### 17.2 质量

- 所有数值型主张具有来源定位。
- 黄金集不存在严重事实错误。
- 抽样分析中，不受支持的陈述低于设定阈值。
- 公式来源、平台推导和编辑判断正确分离。
- 相同输入和版本能够复现相同结构化结果。

### 17.3 新鲜度

- 主要来源新增元数据在 24 小时内入库。
- 高相关候选在每日雷达生成周期内完成初筛。
- 论文更新版本后，旧分析在一次刷新周期内标记过期。
- 新术语候选显示首次观察时间，并在新来源出现后更新状态。
- 新闻、代码和模型发布记录来源发布时间与平台抓取时间。

### 17.4 用户价值

- 用户能否从论文找到前置知识和竞争方法。
- 用户能否从趋势结论回到原始证据。
- 用户是否能解释方法适用边界，而不只是复述摘要。
- 用户是否能区分热点、趋势和得到验证的知识。
- 用户从 Atlas 论文或项目进入 Paperfield 的成功率。
- 用户触发深度分析后，首个可阅读阶段的等待时间。
- 深度档案中可回到原文页码的主张比例。
- 新术语是否能正确关联定义论文、相邻旧概念和采用状态。

不把页面停留时间、点击量或论文数量当作科学质量指标。

### Phase 5：证据到洞察闭环

状态（2026-08-12）：已在 Research Atlas 0.8.0 中交付，137 项自动化测试和 320/390/1024/1440px 真实浏览器验收通过。

交付范围：

- Paperfield `/api/atlas/catalog` 增量协议使用事件级 payload snapshot、SHA-256、tombstone、watermark 和可重放 cursor；Atlas 不读取 Paperfield SQLite。
- Atlas catalog search 使用 immutable `created_at` snapshot、per-kind row caps、keyset cursor 和索引，避免更新重排与同一时间戳插入混入后续页面。
- dossier 在 claim/evidence 粒度保留 `claim_id`、`evidence_id`、source basis、source SHA-256、locator completeness、版本、模型和提示词；可导出 JSON/Markdown 并深链回 Paperfield。
- 前沿 radar 将论文候选、第一方动态、术语候选和已审核 signal 分层呈现，显示来源诊断、排序分量、成熟度和 `as_of`；排序不是科学质量分数。
- 私人研究回路包含显式 focus profile、保存对象、私人 radar、冻结周报、诊断、SQLite backup manifest、完整性验证、恢复和研究数据导出；公共 bootstrap 不返回这些私有对象。
- migration ledger 在启动前拒绝 future schema，并完整校验版本、名称、checksum、缺失和重复记录；研究数据导入在单事务中完成。

验收门槛：完整 unittest、Python/Node 静态检查、30k 目录搜索性能、事件更新/删除/重放/并发分页、未来 schema 字节不变、迁移篡改拒绝、混合导入回滚、公共/私人投影隔离，以及 320/390/768/1024/1440px 浏览器无溢出和无控制台错误。

### Phase 6：可复现研究工作区

目标：把 Phase 5 的“可读洞察”提升为可复现、可持续跟踪的个人研究工作区。Phase 6 不增加未经审核的科学结论，也不根据浏览行为推断用户兴趣。

交付范围：

- 严格历史搜索快照：首次搜索物化结果行及当时可见字段，后续页只读取同一个快照；论文或项目在翻页期间被改名、删除或更新状态时，不改变已经创建的快照。快照具有所有者、查询 fingerprint、创建/过期时间、结果 SHA-256 和上限，过期后明确返回失效状态并可安全清理。
- 可复用研究视图：用户可以显式保存目录搜索、前沿雷达筛选和关注范围；视图保存筛选条件与证据边界，不保存模型凭据，也不自动触发全文分析。运行视图会创建新的 dated run，而不是静默覆盖旧结果。
- 变化提醒收件箱：只根据已发布 signal、已审核公共知识关系和用户显式关注范围生成私人提醒；论文候选、新闻和第一方动态只能作为待核查线索，不能升级为“研究结论”。提醒保存来源 revision、首次/最近命中时间、已读状态与去重键。
- 证据包导出：把视图定义、运行时间、搜索快照、论文 dossier claim/evidence、source SHA-256、定位完整度、反证与未知项放入版本化 JSON/Markdown bundle；导出结果包含 manifest 和 bundle SHA-256，可独立校验。
- 工作区入口：Research Atlas 的私人研究回路增加“研究视图”“变化提醒”“证据包”三个操作面。Paperfield 仍负责精读与源码，Atlas 不直接读取 Paperfield SQLite。

安全与生命周期：

- 所有 Phase 6 写接口继续保持 loopback-only 和同源校验；公共 bootstrap 不返回保存视图、提醒、快照或私人导出。
- 搜索快照设置 TTL、单快照结果上限、单用户活动快照上限和显式清理；清理不删除论文、项目、dossier 或审计历史。
- 视图运行、提醒已读、证据包导出均写入可追踪 revision 或 audit event；导入先完整验证，再在单事务中写入。
- 页面打开、搜索输入和视图预览不得触发外部模型调用；只有现有的显式深度分析授权流程可以处理全文。

验收门槛：

- 翻页期间修改标题、摘要、状态或 tombstone 后，同一 snapshot 的历史字段与结果总数不变；新搜索反映新状态。
- 快照过期、伪造 cursor、跨查询 cursor、超限和清理均有回归测试，不泄露其他私人对象。
- 保存视图的创建、更新、运行、导出、删除和导入保持幂等或有明确 revision；重复 source revision 不产生重复提醒。
- 证据包 SHA-256 可复算，缺失 locator、反证或全文材料时保留 `insufficient_information`，不得补写推测。
- 完整 unittest、Python/Node 静态检查和 30k 目录性能通过；320/390/768/1024/1440px 无横向溢出、控制台错误或焦点逃逸。

### Phase 7：可靠重试与运行差异

状态（2026-08-12）：已在 Research Atlas 0.9.2 中实现。

目标：让可复现工作区在网络超时、重复点击和浏览器重试下仍只产生一个研究运行或证据包，并让相邻运行之间的目录变化可检查、可哈希，但不把元数据变化包装为科学结论。

交付范围：

- 研究视图运行和证据包导出支持 owner-scoped 持久化幂等键；同一键与同一请求返回原资源，同一键用于不同请求返回冲突。
- 搜索型运行的重试不会再次物化快照；前端在服务确认前保留会话级操作键，确认后清理。
- 每个 owner/view 使用从 1 开始单调递增的 `run_sequence` 表示真实运行顺序；每次运行只保存相对相邻前序的新增、移除和元数据变化，附 `previous_run_id`、delta JSON 与 SHA-256；首轮明确标为 baseline，同秒运行也保持确定顺序。
- 证据包纳入运行 delta 和 delta SHA-256，同时继续保留原结果 SHA-256、snapshot、未知项和定位边界。
- 快照清理区分维护调用与新建调用：容量恰满时的纯清理不提前淘汰，新建第五个快照时才按 LRU 释放一个位置。
- schema v10 增加运行差异字段和私有操作幂等账本；schema v11 增加运行序号，并在 v10→v11 迁移中按 SQLite 插入顺序线性化历史运行、重建相邻前序与 delta、同步并重签 Phase 7 证据包。无 delta 字段的 Phase 6 证据包保持原字节；公共 bootstrap 不投影幂等键或私人运行对象。
- 私人工作区 schema 2 导入在写入前联合验证目标 owner 已有运行和待导入运行：每个视图恰好一个 baseline、序号连续、前序严格相邻、时间不倒退，且不存在多 baseline、跳链、分叉、断链或循环；delta 必须由真实前序结果逐字段重算一致。

验收门槛：同键重试资源 ID/字节一致、异请求冲突、owner 隔离、运行差异 hash 可复算、同秒运行严格排序、伪造跳链/多 baseline/分叉拒绝、v9→v10→v11 原子迁移、满容量边界、HTTP 首次 201/重放 200、完整回归与浏览器矩阵通过。

## 19. 对实现 agent 的约束

1. 开始前检查 `git status`，保留当前所有未提交修改，不得重置工作区。
2. Research Atlas 使用独立应用和数据库；不得直接打开、写入或锁定 Paperfield 的 SQLite 文件。
3. Paperfield 只增加配置化 Atlas URL、上下文按钮、深链接和桥接发送端；不得把 Atlas 功能继续塞进 `app.py`。
4. 先完成黄金集闭环，再启动四万篇批量任务。
5. 所有生成输出使用明确 JSON Schema，并有失败与重试状态。
6. 所有批量任务默认关闭，通过配置或管理员操作开启。
7. 用户仅打开论文不触发高成本分析；默认必须显式点击，自动模式由用户开启。
8. 第三方仓库只作发现和结构参考，未经许可不导入正文。
9. 新闻、官方博客和社交内容不得提升论文证据等级。
10. 不编造论文结果、公式、硬件能力、开放状态和趋势共识。
11. 具身智能媒体必须区分真实、仿真、遥操作和生成内容。
12. 每个阶段运行各应用自己的测试，并补充跨站深链接、消息协议、溯源、证据和趋势契约测试。

## 20. 建议的第一张实施工单

第一张工单只建立 companion 边界，不生成前沿内容：

1. 建立独立 `paperfield-atlas` 应用骨架和私有数据库，以前沿雷达骨架为默认首页，并提供空的论文档案页与分析任务页。
2. 定义 `CanonicalPaperRef`、`ProjectRef`、深链接格式和版本化消息 JSON Schema。
3. 在 Paperfield 论文详情或阅读台中增加配置化的 `查看系统讲解` 与 `加入深度分析` 按钮，在项目详情中增加 `查看研究关联`；保留现有一级导航和阅读 UI。
4. 在 Atlas 中实现 `在 Paperfield 精读` 与 `在 Paperfield 查看源码`，验证 `?paper=` 和 `?project=`；对未知本地 ID 明确显示 `尚未导入 Paperfield`。
